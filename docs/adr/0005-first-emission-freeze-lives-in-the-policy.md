# 首发冻结落在 `pin` 的策略里 —— 而这一条是**反转**过来的

「首发冻结」是：一部作品一旦以某个来源下发过，**来源就不再更换**。
本 ADR 记的是**它落在哪一层**，以及为什么最初选的那一层**根本不成立**。

## 背景

M-Team 是第二个数据来源（见 ADR-0004）。换来源必然换 infohash ——
馒头是私种、`info.source` 被改过，所以同一部作品在两边的 infohash 不同。
于是「换来源」在客户端眼里就是**一份新内容**：磁盘上多一份，而且没有任何告警。

所以设计里有一条硬规则：**来源只可能出现在首次下发**；唯一的出口是运维显式做的
「重置」（删掉两处 + `kill -HUP`）。

问题只剩下：**这条规则由谁执行？**

## Considered Options

- **放在 M-Team 装饰器里，不给 `pin.json` 加字段（最初选的，后来被推翻）。**
  M-Team 层对已钉住的作品「原样放行」（连问都不问），并读 pin 表判断「下发过没有」。
  理由是：动 `pin.json` 的 schema 是这个仓库最贵的一类改动（它承载 guid 的稳定性），
  而这一位的收益看起来只是「措辞更集中」。

- **放在 `pin` 的策略里，`pin.Record` 记住来源（现在选的）。**
  候选池的来源与 pin 的来源不同 ⇒ **永不切换**。

## 为什么最初那个选项不成立

**因为决定最终发哪条磁链的不是 M-Team 装饰器，而是 `pin` 的策略。**

装饰器把候选池交给 `pin`，而 `pin` 的 `KeepOrSwitch` 会按既有的规则
（出现 cnsub 就切）**重新决定**。于是「原样放行」根本不是中立动作：

1. M-Team 层对已钉住的作品原样放行 —— 放行的是**上游那个候选池**；
2. `pin` 的策略拿到它，按 cnsub/日期判定「上游那条更好」；
3. **pin 被换回上游** —— guid 抖回去（客户端多下一份），而且馒头从此再也不生效。

这个 P0 是被**票 07 的 Docker 验收**（真 M-Team）抓到的，而当时 6 张票的测试全绿 ——
因为**所有测试都只渲染一次**，而它只在第二次渲染才现形。
现象记在票 09；当时的日志是：

```
WARN: pin 切换 —— 旧磁链=e8556ddc…（馒头那条）新磁链=ec52393f…（上游那条）
```

同一条改动还修掉了一个同根因的症状：`pin` 把记录投影回磁链时不带来源，
于是**只要策略保留了馒头那条 pin**，`<enclosure>` 就会退回一条**磁力** ——
而私种的裸磁力是死链。

## Consequences

- **`pin.json` 多了一位 `source`**（`upstream` / `mteam`）。零值 = 上游，因此旧文件照读；
  写错名字**拒绝启动**，不静默当上游（猜错的后果是那部作品的种子地址变成死链）。
  它是**可读的名字**而不是数字：那份文件是给人手工改的（README 把「删掉某一条」
  当成正式的运维手段），一个数字位会让那件事变成猜谜。
- **上游 pin 的既有行为不变**：同一个来源内出现 cnsub 仍会切（那是 followups 票 09 定的）。
  跨来源永不切换。
- **冻结只有一处实现**（策略），而不是「上层放行得恰到好处」——
  后者要靠每一个新装饰器都记得「别动已钉住的」，而那是一张迟早会漏的网。
- **教训（写给下一个读的人）**：判断「某条规则该落在哪一层」时，
  问的应该是**谁做最终决定**，而不是「哪一层加字段更便宜」。
  这个仓库为前者付了一次 P0 的学费。
