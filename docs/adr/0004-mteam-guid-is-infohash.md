# M-Team 的 guid 仍是 infohash —— 为此每个命中下载一次种子

服务增加第二个数据来源 M-Team（一个私有 PT 站），**只在 `/rss/want.xml` 上生效**：
你在 App 里标了「想看」的作品，如果馒头上也有，就发馒头那一份。

feed 条目的身份（`guid`）**仍然是 infohash**，一字不改。而 M-Team 的搜索与详情
**都不给 infohash** —— 所以为了这个身份，本服务必须把 `.torrent` 下载回来自己算，
并把它存下来，通过 `GET /torrent/{infohash}.torrent` 交给客户端。
**代价是实打实的：每个命中消耗一次种子下载配额（站点建议 100 个/小时），
外加一份本地存储与一个 bencode 解析器。**

## 背景

**为什么需要第二个来源。** 只有一个具体场景：几年前的老片，JavDB 上的磁链慢得下不动，
而馒头上很快。用户的原话是「M-Team 只是用来解决这个问题的」——它不是「更好的来源」，
它既不如 JavDB 新、也不如 JavDB 全（用户的原话）。

**为什么身份这么贵。** `guid` 就是 infohash，而「选哪条磁链」决定 infohash。
pin 之所以存在（followups 票 04/08/09），就是因为上游的候选顺序不可重放 ——
不钉住的话，候选列表一变、`guid` 就变，客户端会把它当成新内容**静默**重复下载一份。
因此引入第二个来源时，第一个要回答的问题就是：**它的条目拿什么当身份。**

**M-Team 给不出身份（已实测，不是推测）。** `POST /api/torrent/search` 每一行的
`infoHash` 都是 `null`；`POST /api/torrent/detail` 的 50 个字段里也有 `infoHash`，
**值同样是 `null`**，且没有 `torrent` 子对象、没有 `magnet`。四个先例项目
（PT-depiler / Jackett / MoviePilot / `llbox/mt-sdk`）**没有一个用 infohash 做身份**
—— 本服务是第五个，也是唯一一个为它付代价的。

**它是私种，所以「合成一条磁力」也不通。** announce 里带的是一份**按种子、按次签发的
凭据**（`https://tra1.m-team.cc/announce?credential=base64(sign&t&tid&uid)`），
而它**只存在于 `.torrent` 文件里** —— `x-api-key` 换不到。因此：不含 announce 的磁力是死链；
含 announce 的磁力会把一份账号维度的凭据写进 feed。

## Considered Options

- **`guid` = infohash（选它）。** 代价：每个命中下载一次种子（回填 234 部 ≈ 2.3 小时，
  受 100 个/小时的建议速率约束）、要存 `.torrent`（约 10–25MB）、要写一个 bencode 解析器
  ——而那个解析器是本轮**唯一能静默算错 guid** 的地方。收益：`CONTEXT.md` 里
  「infohash 是本 context 唯一被信任的作品身份」这条不变量**原样不动**，
  pin 的整套语义（以及它的测试）不需要为第二个来源改一个字。
  ⭐ 附带一个不显眼但重要的好处：**enclosure 变成自包含的** —— 客户端拿到种子之后
  不再依赖本服务，也不依赖任何会过期的下载令牌。

- **`guid` = M-Team 的 torrent id。** 不下载、不存储、不解析，回填只要几分钟
  （只吃搜索配额，1000/24h 富余），enclosure 指向本服务一个端点、现场换令牌再流出去。
  **否掉**，理由不是「纯粹」：它把 `guid` 的稳定性寄托在**上游数据库的行**上 ——
  馒头重建一个种子，id 就变，客户端重下一份。而「上游重建内容导致身份改变」恰好是
  这个项目花了两张票（04/09）在消灭的那类抖动。用它换来的「回填快 2 小时」是**一次性**的，
  而身份的不稳定是**永久**的。

- **交馒头自己的 `genDlToken` 链接。** Jackett 与 MoviePilot 都这么做，最省事。
  **否掉，而且后来实测证实了**：那条链接**生成后约 5 分钟就失效**
  （`{"code":"1","message":"連結不可用！ 超出有效期"}`），
  而 qBittorrent 是稍后才去取的。另外**我们反正要下一次种子才能算 guid** ——
  既然字节已经在手里，再让客户端去求一次上游就只是多一个会坏的环节。

- **合成磁力，`tr` 指向真 tracker（带凭据）。** 磁力自包含、不依赖本服务。
  **否掉**：feed 里从此带凭据，而且没法验证客户端能否取到 metadata
  （见下一条，那是同一个未知数）。

- **合成磁力，`tr` 指向本服务做 announce 中转。** 一度是用户的想法（为了隐藏凭据）。
  **否掉，而且否掉的理由是技术性的**：tracker **只提供 peer 地址，不提供 metadata**。
  若合成磁力取不到 metadata，原因是 peer 不肯做 BEP 9 交换，中转把 announce 代理给
  馒头会拿到**同一批 peer**，同样失败 —— 它修不了它想修的问题。
  它唯一买到的是「凭据不出本服务」，而「本服务自己发 `.torrent`」免费拿到同样的效果，
  却不必把那条 `tr` 永久写进客户端的 metadata 里（那意味着本服务停机、换端口、换 IP
  都会让所有已发出的种子**永久**停止 announce）。

- **不做（继续只支持 JavDB）。** 否掉：这是用户的原始需求。

## Consequences

- **配额账。** 搜索 1000/24h（234 部想看只占 1/4，富余）；**种子下载 100 个/小时是唯一的瓶颈**，
  因此回填是**渐进**的：首次要几小时，期间那些作品不在 feed 里 —— 但**不静默**，
  want.xml 的标题里有一个「N 部待定来源」的计数在下降（复用既有的「待磁链」写法，
  因为 qBittorrent 拿不到 channel description，只呈现标题）。
  稳态没有这个问题：新加一部，一个轮询周期内判定完。

- **本地存储与权限。** `.torrent` 与判定表同目录、权限 0600 —— 因为**种子里带凭据**。
  三套部署方式都要给这个目录可写（照 README 里 pin 那一节复制一遍）。
  判定表本身**可以丢**（重建只是贵），这与 pin（丢了就重复下载）是**不同**的状态，
  所以它们不放在同一个文件里。

- **字节存下来**（✅ 已定，2026-10-13）。客户端取种子只依赖本服务，不依赖馒头 ——
  这与「本服务自己发种子」的初衷一致。凭据**长期有效**：
  用户观测，qBittorrent 里几个月前加的馒头种子现在仍正常汇报（凭据按次签发，
  但显然不按时效验；否则全站种子都会红）。
  ⚠️ **残余风险（要写进 README）**：凭据绑账号。**用户重置 M-Team 的密钥/passkey 后，
  我们存过的每一份种子都会死，而且修不了** —— 唯一出口是逐部「重置」，
  而那会换 `guid`、重新下载一份。换句话说：**密钥轮换 = 一次（有界的）重复下载**。
  代价换来的东西：馒头瞬时不可用时，客户端仍能取到种子。
  **否掉的**：「每次现取」（凭据永远新鲜、也能自然熬过密钥轮换，且省 10–25MB；
  但把「客户端取种子」变成同时依赖本服务与馒头都在线 —— 而 RSS 本来就在
  定时轮询，让每一次取件都多一个可坏的外部环节，不划算）。

- **凭据暴露面（新增，且比现状严重一档）。** 本服务发出的 `.torrent` 里带着一份
  **账号维度的 tracker 凭据**（按种子、按次签发），而本服务不做鉴权 ——
  谁能访问它，谁就能拿到它。站点明文写着凭据泄露要重置。
  隔离由 k8s 集群内 Service（qBittorrent 就在同一个
  集群）与 edge 的 authelia 提供。**这条要写进 README 最显眼处。**

- **`CONTEXT.md` 的「上游」不再是单数。** 它是全仓库使用频率最高的领域词之一，
  而这一轮之后「上游」只指 JavDB，M-Team 是另一个数据来源。
  不写清楚的话，下一个读的人会把 M-Team 的凭据失效当成「上游坏了」接进 `/readyz`
  或 liveness —— 而那是错的：换 key 不是重启能解决的。

- **待验证的东西被清掉了两批。** 原来列在「否决性」位置上的 `mode: adult` 能否按番号
  搜到 AV —— **已实测通过**（5 个真番号里 4 个命中，严格匹配零误配）；
  凭据寿命 —— **已由用户观测结掉**（几个月前的种子仍正常）。
  本轮剩下的未知都是工程性的（见 map 的 Not yet specified），不再有能推翻设计的。
