全量为什么慢？

全量要把这位女优的全部作品拉完再逐条取磁链（一位约 5 页、200 多次上游请求）。 一次挑很多人又都选全量，一轮轮询可能要好几分钟 —— 只有补旧作时才用。

    基本 main —— 这组走 filter_by，不走 filter_by_tags
    链接范围

    标签

    最多选 5 个 · 已选 0/5

    分组名、顺序、组内标签全部取自上游 /api/v2/tags?type=0。最多 5 个不是我们的约定 —— 实测第 6 个 id 会被上游静默丢弃 （同一个 id 挪到前 5 位就生效，同一批请求的结果从 1 条变成 0 条）， 所以上限只能是 5。多个标签之间是交集。

    时间与时长

    上游把这三组和标签放在同一个响应里，但它们的 id 不是标签 id：月份 1–12 与真标签 id 完全撞号（3 = 服裝:眼鏡），時長 的 id 形如 lt-45；试过的 30 个参数名在 4 个端点上又全部被 静默忽略。所以这三组不走上游，由本服务按 release_date / duration 在本地筛 —— 这两个字段在列表响应里 100% 出现。

    月份

    时長（lt-45 / 45-90 / 90-120 / gt-120） 这一版不做 —— 它需要一条本服务自己的 duration= 过滤， 而这个需求还没定。放在这里只是为了不让人以为漏了。

    实测证据与复跑命令
    • filter_by_tags=45-90 与 =45 返回 逐条相同的 6 部 —— 非数字 id 被截到了数字前缀 45（類別:第一人稱攝影），而这 6 部的时长全部 > 90 分钟。
    • filter_by_tags=gt-120、=2026 → 0 条。
    • year=2020 / month=3 / duration=lt-45 / movie_filter_by=… 在 /movies/tags、/movies/latest、/movies/top 上全部与基线逐条相同。
    • 复跑命令见 notes/lists.md 第 2 节。
