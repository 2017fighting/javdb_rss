# 04 — 磁链选择：顺序无关，还是接受风险

**What to build:** 同一部作品有多条磁链候选，服务按上游返回的顺序取第一条（若其中存在中文字幕版则取它）。而 feed 条目的 `guid` 就是被选中那条的 infohash —— 因此**上游顺序一变，选中的磁链就变、guid 就变，qBittorrent 会再下一份**。

这属于「不会被发现」的失败：磁盘上多一份文件，没有任何告警。所以它值得一张票，而同类的 TLS 指纹 / WAF 不需要 —— 后者一旦出问题会变成可见的 502。

## Answer（2026-09-30，grilling with user）

**决策：把选择改成「按 `created_at` 取最新、cnsub 优先」的确定性规则，并把每个作品 id 已选中的磁链持久化「钉住」；只有出现新的 cnsub 时才切换。**

1. **选择规则（纯函数，替换 `catalog.Select` 的定位）**：候选里有 `cnsub=true` 的 → 取 `created_at` 最新的那条 cnsub；否则 → 取所有候选里 `created_at` 最新的。`created_at` 相同用 infohash 字典序定序。**不读取切片顺序。**
2. **钉住（新增持久状态）**：服务端记住每个作品 id 已下发的 infohash，后续请求继续返回它，**除非上游出现了新的 cnsub**（则切到最新的 cnsub 并更新记录）；无 cnsub 的作品不再受上游后续新增普通磁链影响。
3. **对原「信任 App 顺序」的关系：推翻它。** 原槽位规则只在「有/无字幕」之间选，候选之间的排序仍交给上游；现在改为本服务按 `created_at` 自行定序，并在首次选定后锁死。

**为什么不是别的选项**：

- 实测（211 部作品，真实 API）证明上游顺序**既不是旧→新、也不是新→旧**，而是一套看不到的「版本档位 + 未知键（很可能是做种数）」的策展排序；它**不可用任何字段重放**（最好的 `hd 优先` 只解释 218/300）。因此无法既「信任上游排序」又「顺序无关」。
- 「顺序无关的纯函数」本身与当前选择只一致 **147/197（≈75%）** —— 首次选定会换掉约 1/4 作品的磁链。用户接受这个代价，并额外要求**钉住**来消除后续抖动（含无 cnsub 作品被上游新增普通磁链带动的变化）。
- 依据仍是项目原则：重排的失败**不可见**，而「宁可看见错误，不要静默降级」。「接受风险」被排除了。

**已知代价（已向用户说明并确认）**：

- **推翻地图里已定的「无状态」（服务端不持久化已下发）** —— 这是有意的例外，需要新的存储与失效设计（新票 08/09），并与「URL 即订阅」、k8s 只读根文件系统/多副本重新对齐。
- `created_at` 在本端点是 `YYYY-MM-DD`（日粒度）：同日多条靠 infohash 定序，「新 cnsub」只能在日粒度上判断。
