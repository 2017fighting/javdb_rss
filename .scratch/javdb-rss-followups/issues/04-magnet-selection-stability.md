# 04 — 磁链选择：顺序无关，还是接受风险

**What to build:** 同一部作品有多条磁链候选，服务按上游返回的顺序取第一条（若其中存在中文字幕版则取它）。而 feed 条目的 `guid` 就是被选中那条的 infohash —— 因此**上游顺序一变，选中的磁链就变、guid 就变，qBittorrent 会再下一份**。

这属于「不会被发现」的失败：磁盘上多一份文件，没有任何告警。所以它值得一张票，而同类的 TLS 指纹 / WAF 不需要 —— 后者一旦出问题会变成可见的 502。

交付：**一个决策**，不是一段代码。

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] 已记录现有证据：同一批作品连续多次请求，顺序完全一致（已做过）；跨天/跨周未知
- [ ] 做出决策：改成**顺序无关**的确定性选择（例如按「中文字幕优先 → 体积降序 → infohash 字典序」），或明确接受风险
- [ ] 若选择改：新规则是纯函数、有测试，且**不读取上游顺序**
- [ ] 若选择改：说明它与用户原先「信任 App 顺序」这个取舍的关系（是推翻了它，还是只在候选之间定序）
- [ ] 决策与理由落进笔记；若选择接受风险，写下「为什么不改」而不是留空
