# 08 — 「钉住」磁链的存储与失效

**What to build:** ticket 04 的决策要求服务端**持久化**「每个作品 id 已选中的 infohash」（pin），只有出现新 cnsub 才切换。这是本服务引入的**第一个持久状态**，直接抵触地图里已定的「无状态：服务端不持久化已下发」。本票把这个新状态设计清楚，让「钉住」在裸二进制、容器、k8s 三种部署下都有明确行为。

设计上，pin 天然落在既有的 `catalog.Source` 边界上 —— 与 `dedupe` 同层，做成一个装饰器；`Select` 保持为纯函数（ticket 04 的排序规则）。本票只定「状态存哪、怎么活」。

**Type:** grilling（交付是存储与失效的设计决定）

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] **介质与位置**：文件（JSON/行式日志）还是嵌入 KV（SQLite/bbolt）？放在 `token_file` 同级的可写目录？裸二进制要开箱即用；容器要能挂卷
- [ ] **重启语义**：pin 丢失会怎样？重新按纯函数选会不会换 guid（=重复下载）？能否从上游重建出同一选择？（若不能，说明丢状态就是丢 guid）
- [ ] **多副本 / 并发**：两个实例会不会各钉一套、给出两个 guid？是否需要 single-writer 或「只允许单副本」的明确约束？
- [ ] **增长与淘汰**：作品会无限累积。TTL？容量上限？超限时的行为（淘汰最旧？拒绝写入并告警？）
- [ ] **键的选择**：「每个 id」是 movie id 还是番号？折号不唯一（合集/同名），movie id 才唯一
- [ ] **跨 feed 共享**：同一作品同时出现在 `/rss/code/...` 与 `/rss/actress/...` 时，必须共享同一个 pin，否则同内容两个 guid（破坏跨 feed 去重）。这条要写进测试
- [ ] **写失败**：磁盘满 / 只读根文件系统时，报错可见还是降级？依据仍是「宁可看见错误」
- [ ] **与 k8s 清单的一致性**：现有 deploy 是只读根文件系统 + 无卷。要么给 pin 加卷（PVC/emptyDir + 明确语义），要么在清单里写死「多副本不支持」

## 与 ticket 09 的边界

本票定**存哪、怎么活**；「什么时候切换 pin」由 [09](09-pin-switch-semantics.md) 定。两者无天然先后，可并行。
