## 结论一览

| 条目 | 结论 | 落在哪 |
|---|---|---|
| `filter_by_tags` 是否生效 | **生效**（先前记「未确认」是误判） | `actress-params.md` 正文 + 复勘记录 §3 |

| `i` / `v` 的含义 | `i` = 有预览图（`has_preview_images`），`v` = 有预览视频（`has_preview_video`） | 复勘记录 §1 |
| `i` / `v` 的出处 | 先前记的「来自上游 `filter_tags`」**是错的** —— 上游只给 `p`/`s`/`m`/`c` 起名；真出处是先例项目的 `MainFlags` | 复勘记录 §2 |
| 主属性逗号列表 | **AND 交集**，且**顺序无关**（63 个组合全集验证） | 复勘记录 §5 |

| `size` 单位 | **MiB（2^20 字节）**，不是十进制 MB | 复勘记录 §6 |

## 实测与实现（2026-10-01）

**工具**：新增 `cmd/contractprobe`（入库、可复跑）。它复用 `internal/appapi`
的传输层与签名，因此发的请求与服务发的**逐字节同类**；原始响应落盘为证据。
命令：`actor` / `letters` / `props` / `tags` / `sort` / `combo` / `magnets` /
`raw` / `collected` / `session`。

**为什么把它入库**（对照 ticket 04 的 `cmd/magnetprobe` 用完即删）：
那张票的结论是「顺序不可重放」这种一次性取证；而本票的条目是**长期要能复核的
契约断言** —— 上游改一次契约，应当能原地重测，而不是重写一个探针。

**顺手改掉的代码**（复勘把「推测」变成了「事实」，代码就该跟上）：

- `catalog.Magnet.SizeMB` → `SizeMiB`（旧注释写的是「假定为兆字节」）。
  `internal/feed/rss.go` 里 `enclosure length` 的 `* 1024 * 1024` 本来就是对的，
  只是当时没依据；指向「未核实单位」的陈旧 `TODO` 已删。
- `pin.json` 的 `size_mb` → `size_mib`，并**读入旧键做迁移**。不做这层兼容的话，
  一次「读旧文件 → 写回」会把每条 pin 的体积静默清零 —— 有单测
  `TestLegacySizeMBKeyIsMigrated` 钉住，并做过变异验证（去掉迁移即变红）。

## 复勘暴露的新未知（按票面要求登记）

1. **`tags[].videos_count` 与 `filter_by_tags` 实得条数口径不同**：
   EvkJ 的 80 个标签里 15 个对不上，且**两个方向都有**
   （`212`(VR) 声明 48、实得 27；`48`(蕩婦) 声明 26、实得 27）。
   「实得更多」这一侧排除了「被分页截断」这个解释。原因未查。
   **影响**：不能拿 `videos_count` 当「筛选后会有多少条」的预期。
   已登记进 `notes/actress-params.md` 的复勘记录（「仍然没有结论的」）。
2. **`i`/`v` 没有上游文案佐证** —— 含义是从字段反推的（三个女优样本一致）。
   若上游某天让某个字母的划分与另一个字段巧合重合，这套方法会认错。
   代价很轻：认错只会让筛选条件选错，且是**可见**的（feed 内容不对）。
3. **服务端是否按 `device_uuid` 做统计/风控不可观测** —— 那是服务端内部状态。
   代价可接受：真出问题会变成可见的失败。

以上三条都不构成新票（都是「可见的未知」或「代价很轻」），因此记在笔记的
「仍然没有结论的」一节，而不是开票 —— 判据沿用本 effort 的一贯原则：
**会被发现的未知可以接受，不会被发现的不行。**
