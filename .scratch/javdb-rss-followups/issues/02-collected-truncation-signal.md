# 02 — `/collected` 的截断不再静默

**What to build:** `/collected` 按页拉取收藏列表，翻页有上限。收藏数一旦超过上限，它会**静默返回一份不完整的列表** —— 用户无法分辨「我就收藏了这么多」与「服务只读到了这么多」。这是本服务唯一会静默少给数据的地方，也正是本项目反复要避免的那一类失败。交付：达到上限时给出明确信号。

**Blocked by:** None — can start immediately.

**Status:** resolved

- [x] 达到翻页上限时，响应里有**可机读的明确信号**，而不是照常 200 + 残缺列表
- [x] 有测试构造超限场景并断言该信号出现
- [x] 未达上限时响应**不含**该信号（不能是一个永远为真的字段）
- [x] 上限的取值有据可依：先实测上游分页的每页条数，再决定留多少余量

## 实测与实现（2026-09-30）

**每页条数实测**（真实 token，逐页拉完）：每页固定 **10 条**；144 位收藏 = 15 页
（14 满页 + 1 页 4 条），第 16 页为空。`maxCollectedPages = 20` = 约 200 位上限，
是当前 144 位的约 **1.4 倍**（多出 56 位、5 页）。

**信号形态**（与用户 grill 选定）：达到上限时返回 `200` + 已读到的部分列表，
额外带三个**仅触顶时出现**的字段：`truncated: true`、`pages_fetched`、`max_pages`。
未触顶时三者完全不存在（`omitempty`），消费方靠「键是否存在」判定完整性。

**实现点**：`catalog.Collection` 值类型（`catalog/source.go`）承载信号，
`appapi.Client.CollectedActresses` 在前 20 页都非空时**再探一页**：探针非空才置
`Truncated`（把信号精确到「还有更多」，而不是「踩到了上限」，因此恰好收藏 200 位
不会误报）；`dedupe` 装饰器原样转发（有测试钉住它不吞信号），
`httpapi.handleCollected` 输出字段并记 WARN 日志；`login` 的验证输出也会提示截断。
