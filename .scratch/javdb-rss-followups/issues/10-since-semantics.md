# 10 — `since` 的语义定稿

**What to build:** `?since=<日期>` 的**比较语义** —— 一个能写进 `## Answer` 的决定，不是一段代码（落地见 [11](11-since-landing.md)）。

**Type:** grilling（交付是决定）

**Blocked by:** None — can start immediately.

**Status:** resolved（2026-10-05，grilling with user；落地见 [11](11-since-landing.md)）

## 这张票为什么存在（一段错位史）

初次交付地图的票 09（[`../../javdb-rss/issues/09-cost-cache-throttle.md`](../../javdb-rss/issues/09-cost-cache-throttle.md)）在票面里写下了自己的欠账：

> 本票仍需回答的是：**这个临时语义对不对**，以及上面 Q2/Q3/Q4……

临时语义由票 03 抢先落地：比 `release_date`、字典序 `>=`、**解析不了的一律保留**、每次启用打一条 WARN。但票 09 的 `## Answer` 只回答了缓存 / 并发 / 限流 / 翻页 —— **「这个临时语义对不对」从未被回答，票却标了 `resolved`**。于是今天：

- 三处 live code 仍写着「尚未定稿」（`internal/catalog/model.go` 与 `internal/config/config.go` 的 `TODO(ticket-09)`、`internal/httpapi` 的 WARN 与注释）；
- 记录层却说它已解决（`../../javdb-rss/map.md` 的 `## Not yet specified` 清理记录）—— 那处订正见 [12](12-record-integrity.md)。

本票是这条**孤儿欠账**的接收方。

## 要定什么

1. **比较字段**：作品的 `release_date`，还是被选中那条磁链的 `created_at`（也就是 `pubDate` 的来源）？
2. **区间**：`>=`（闭）还是 `>`（开）？边界那天的作品留不留？
3. **坏数据**：`release_date` 为空、或 `created_at` 两种格式都解析不了时，留还是丢？
4. **定稿后那条 WARN 何去何从**：删掉，还是换成只对「坏数据」报警？
5. **范围与不对称**：本决定对两条路由都生效（`/rss/actress/{id}.xml` 与 `/rss/list/{id}.xml` 都调 `filterSince`）。但两条路由的 `year`+`since` 处理**目前不对称** —— actress 判 400 并说明原因，list 只把 `year` 透传给上游。顺带定要不要对齐。

## 已经知道的事实（不要重新试探）

- **作品层只有 `release_date`**：三个列表端点共用的 `movieSlim` 就是
  `id/number/title/release_date/has_cnsub/magnets_count`。电影级**没有**「上架时间」这种字段。
- 所以「上架时间」的真实候选是**被选中那条磁链的 `created_at`** —— 也正是 feed 里 `pubDate`
  的来源。而 `catalog.ParseCreatedAt` / `CompareCreatedAt` 已经吃下线上两种格式
  （`01/02/2006`、`2006-01-02`，见 `internal/catalog/createdat.go`，followups 09 建的）。
  **因此「要解析时间」不构成否掉这个选项的理由 —— 落地成本已经很低。**
- 于是问题不是「哪个字段存在」，而是**「新」对用户意味着什么**：作品发行得晚，还是上游有人
  新发了磁链。**合集再版**是两者的分歧点 —— 旧 `release_date`、新 `created_at`；
  按前者它今天被静默丢掉。
- 已记录的副作用（`../../javdb-rss/notes/actress-params.md`）：`pubDate` 取 `created_at`，
  而过滤比的是 `release_date` —— **两个日期不同源**，所以过滤后仍会出现 `pubDate` 早于
  `since` 的条目。选 `created_at` 会让这两个日期自洽。
- 默认只取第一页（最新 50 部，**按 `release_date` 倒序**）。若改比 `created_at`，
  「新作品必然在顶部」这个前提要重新检查一次。

## Answer（2026-10-05，grilling with user）

**决定：`since` 比作品的 `release_date`，闭区间 `>=`；非法输入一律 400；日志只报异常，正常路径一条 Debug。**

实质性结论与票 03 落地的临时语义**一致**，但它当初「对不对」从未被论证，且实现方式上有三个静默失败（见下文 § 实测）需要一并修掉。

### 0. 票面勘误（写票时没实测，错了两处）

1. 「**合集再版**是两者的分歧点 —— 旧 `release_date`、新 `created_at`；按前者它今天被静默丢掉」—— **方向写反了**。
   实测 `OFJE-662`：`release_date`=2026-09-29，唯一一条磁链 `created_at`=**2020-09-22**。
   新上架的合集**复用六年前的磁链**：按 `release_date` 保留它，按磁链时间才丢它。
2. 「本决定对**两条**路由都生效」——**少数了一条**，是**三条**（女优 / 清单 / 全站 `/rss/tags/`）。
   同理，我另写了一版「清单路由缺 `year`+`since` 的 400」也是错的：清单路由由 `buildEntityMask`
   直接拒绝 `year`（实体字母不是 `a`）。真正没挡的是**全站路由**。

### 1. 实测（真实 API；证据见 [`../../javdb-rss/notes/api-recon.md`](../../javdb-rss/notes/api-recon.md) §10.4.2）

女优 `EvkJ` 第 1 页 50 部（`release_date` 跨度 378 天）：

| 事实 | 数 |
|---|---|
| `release_date` 严格 `YYYY-MM-DD` | **50/50**，空 0 条 |
| `magnets_count = 0`（永远成不了 item） | **33/50** |
| 选中磁链 `created_at` 比 `release_date` 新 / 同日 / 旧 | 11（最远 **+196 天**）/ 1 / 5（最远 **-2198 天**） |
| `since` 取「最近 30 天」时两条规则各留 | 按 `release_date` **6 部**（真成为 item 的只有 **1** 张）；按磁链 `created_at` **0 部** |

拿**真实现存函数**（`filterSince`）跑的输入形状实测：

| `since` | 结果 |
|---|---|
| `2026-01-01` | 正确 |
| `2026-1-1` | **静默丢掉 1–9 月**（6 部只剩 3 部） |
| `hello` | **静默只留 1 部**（等同空 feed） |
| `2026-01-01T00:00:00Z` | **静默丢掉当天发行的作品** —— 只丢边界那一天，其余看着完全正常，而它坏掉的正是**订阅链接生成器**发 `since=<今天>` 这个最常用的取值（复验：`2025-12-31` / `2026-01-15` / `2026-01-31` 均照常判断） |
| `2026-01-01T00:00:00Z`（或 `2026-01-01 00:00:00`） | **静默丢掉「恰好等于那一天」的作品**（日期部分是这类串的前缀 → 更短即字序更小），其余日期看起来完全正常 |

### 2. 决定

| 情形 | 行为 |
|---|---|
| `since` 缺省 / 空白 | 不过滤（现状不变） |
| `since` 是严格 `YYYY-MM-DD` | 保留 `release_date >= since` 的作品（闭区间；字符串字典序 —— 严格校验形状后它与时间序等价） |
| `since` 形状不严格（`2026-1-1` / ISO 时间戳 / `hello` / `2026-13-45`） | **400**，并说明期望形态 |
| `year`（女优、全站）或 `month`（全站）与 `since` 同时给 | **400**（三条路由同一规则） |
| 作品 `release_date` 为空 | **保留** + 计数 |
| 作品 `release_date` 形状不对 | **保留** + **单独**计数（与「空」分开） |
| 过滤后一条不剩（含 `since` 在未来） | 200 + 空 feed + **一条 WARN** |
| 取数窗最旧一条仍 `>= since`，且末页是满页 | **一条 WARN**：窗口没走到 `since`，拿不到完整下界 |
| 语义正常 | 无 WARN；一条 **Debug**：作品 N / 能成为 item M / 保留 K / 丢弃 D / 坏数据 E |
| `pubDate` | **不动**（仍取选中磁链的 `created_at`），文档写明它可能早于 `since` |

### 3. 被否的选项，为什么被否

- **改用磁链 `created_at`**（或 `release_date` / `created_at` 的**并集**）：它会筛掉真正的新作品。
  实测最近 30 天窗口内它保留 **0 部** —— 磁链的 `created_at` 普遍早于发售日（`SNOS-377` -5 天很常见），
  合集更是差 6 年。而它想救的那件事（旧作品被补上新磁链）**结构上不可达**：
  取数是按 `release_date` 倒序分页的，一部 2020 年的作品被补上新磁链时根本不在第 1 页。
  并集只是把「R 能保的全部」加上一批会突然冒出来的旧作品条目（每条都是一次完整下载），
  实测在女优路由上并集 ≈ R，收益接近零而代价是真的。
- **开区间 `>`**：订阅链接生成器的追新模式发的就是 `since=<今天>`（`todayISO()`，补零 `YYYY-MM-DD`）。
  开区间会让**当天发行**的作品永远进不来 —— 「只追新」反而丢掉最新的那批，且看不出是区间造成的。
- **`since` 形状不对时只打 WARN（现状）**：那就是上面那张表里的三个静默失败。
  用户拿到的是 200 + 错 feed（甚至空 feed），唯一信号在日志里 —— 正是本项目反复禁止的那一类。
  与已有的 `year`+`since` 判 400 是同一条原则：**参数没被听懂就说出来**。
- **`year`/`month` + `since` 只在女优路由判**：那会留下全站路由这个洞。
  全站路由的 `year`/`month` 是掩码里的正当维度，和本地 `since` 同时给必然空 feed，
  而订阅链接生成器的文案已经写着「服务那侧也会判 400」—— 补上才是文案与实现一致。
- **正常路径完全静默 / 打 Info**：静默则两个计数算了没人看得到；Info 则 qBittorrent 每 15 分钟
  每条 feed 一条。Debug 是唯一既不吵又拿得到的档位（`-log-level=debug`）。
- **`pubDate` 改成 `release_date` 或 `max(两者)`**：`pubDate` 的职责是如实转述上游事实，
  而 `OFJE-662` 那条 2020-09-22 是**真的**。改了它，同一个作品在不同 feed 里日期会不同
  （新概念），`max` 更是凭空构造、以后无法从上游复核。qBittorrent 靠 guid 去重、不看日期。
- **`since` 比窗口更旧时自动翻页 / 加机读信号**：自动翻页会把「建库」场景的上游压力变成
  不可预测（`pages=20` 已是为它准备的），而 RSS 没有机读位可放信号（只能塞 channel 描述，
  那是给看 RSS 的人、不是给 qB 的）。因此只 WARN + 把「`since` 只在取到的页里生效」写进文档。
- **丢弃形状不对的 `release_date`**：与「空则保留」自相矛盾，且失败方向是静默少给。
  保留它则失败方向是「多给几条」—— 用户看得见，也符合票 03 定下的那条取舍。

### 4. 定稿后必须跟着改的（→ [11](11-since-landing.md) 的清单）

1. `since` 严格形态校验 → 400；三条路由共用一份校验。
2. 全站路由补 `year`/`month` + `since` 的 400（女优已有；清单靠 `buildEntityMask` 间接覆盖）。
3. `release_date` 空 / 形状不对 → 保留，并**分开**计数。
4. 日志改造：删掉「语义尚未定稿」那条 WARN；正常路径一条 Debug（作品 / item / 保留 / 丢弃 / 坏数据）；
   「筛空」与「窗口没走到 `since`」各一条 WARN。
5. 文案与文档：「尚未定稿」在代码、`config.yaml`/`config.example.yaml`、`notes/actress-params.md`、
   `README.md` 里一并消失；`since` 的语义、`pubDate` 可能早于 `since`、
   「`since` 只在取到的页里生效」三件事写进 notes 与 README；两处 `TODO(ticket-09)` 一并结清。
6. 表驱动单测：闭区间边界日、`since` 四种坏形状各判 400、空 / 形状不对的 `release_date` 保留、
   筛空与窗口未走完两条 WARN 各被触发一次。

### 5. 已知代价（有意接受）

- 窗口（`pages`）决定了 `since` 的下界能走多深，而窗口没走完时只有一条 WARN，没有机读信号。
- 刚上架的合集可能在 feed 里标着六年前的日期 —— 如实转述上游，观感上确实怪。
- 上游一旦改变 `release_date` 的形状，那批作品会被「保留 + 计数」：feed 变多而不是变少。
  这是刻意选的方向（宁可多给几条，也不静默丢）。
