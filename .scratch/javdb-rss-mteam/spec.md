# Spec — M-Team 优先（`/rss/want.xml`）

> 上游决策地图：`.scratch/javdb-rss-mteam/map.md`
> 实测事实（一手/二手分开标）：`.scratch/javdb-rss-mteam/notes/mteam-api.md`
> 决策记录：`docs/adr/0004-mteam-guid-is-infohash.md`
> 词表：`CONTEXT.md` 的 `## Language`（本文一律用它：磁链候选 / 作品 / 想看 / 判定 / 命中 /
> 负结果 / 查询失败 / 首发冻结 / 重置 / 待定来源 / 种子文件 / 钉住 / 上游）

## Problem Statement

几年前的老片，上游（JavDB App 私有 API）给出的磁链候选做种的人很少，**慢得下不动**；
而同一部作品在 M-Team（一个私有 PT 站）上很快。现在我只能在 App 里把它标成「想看」，
而 `/rss/want.xml` 交出来的仍然是上游那份慢的磁链 —— 我看不出这部片馒头有没有，
只能手工去馒头搜一遍、手工下载。而且上游的磁链候选和馒头的候选是**两条不同的下载**
（馒头的种子改过 `info.source`，infohash 不同），手工换过去等于磁盘上多一份，
还得自己记得删旧的。

## Solution

在 App 里标了「想看」的作品，**如果 M-Team 也有，feed 就交出馒头那一份**。

具体是：判定在**后台**做（限速、可续跑），feed 只读判定结果、绝不阻塞渲染；
判定还没就绪的作品**不发条目**，但会在 feed 标题里被计数（`N 部待定来源`）——
不静默少给数据。判定一旦落到「命中」，该作品的磁链候选池**整体换成**馒头的那一组，
于是 feed 交出馒头的**种子文件**（不是磁链 —— 私种的裸磁链是死链），
而 `guid` 仍是 infohash，所以跨 feed 去重、洗版重下、重启不变这些性质一条不丢。

来源一旦定下就**冻结**（首发冻结）：一部作品以哪个来源下发过，之后就不再换。
唯一的出口是**重置**（删判定 + 删钉住 + `kill -HUP`），代价是可能重复下载一份。

## User Stories

1. 作为这个服务的唯一用户，我想让 App 里标了「想看」的作品在 M-Team 上也有时走馒头那一份，这样几年前的老片也能下得动。
2. 作为这个服务的唯一用户，我想让 M-Team 的准入条件就是「我把它标成了想看」，这样我不必再手工维护任何配置文件。
3. 作为这个服务的唯一用户，我想让 M-Team 只作用于 `/rss/want.xml`，这样女优订阅和番号订阅的内容不会因为馒头通不通而变。
4. 作为这个服务的唯一用户，我想让「想看」里 M-Team 没有的作品照旧发上游那份，这样命中率不满时我不至于什么都拿不到。
5. 作为这个服务的唯一用户，我想让「M-Team 没有」这个结论是**永久**的，这样服务不会每轮都去问一遍、白烧配额。
6. 作为这个服务的唯一用户，我想让「没查成」（网络 / 限流 / 凭据）与「查过、没有」分得清清楚楚，这样一次上游抖动不会让一部作品**永久**失去这个功能。
7. 作为这个服务的唯一用户，我想让查询失败**不自动重试**，这样上游抖动不会引发换源、也就是不会重复下载。
8. 作为这个服务的唯一用户，我想让判定还没就绪的作品**不在 feed 里发条目**（但计入标题），这样我不会以为服务没读到那张清单。
9. 作为这个服务的唯一用户，我想让 feed 的标题里同时看到「N 部待磁链」和「N 部待定来源」，这样我能分清是馒头还没出种还是服务还没判定完。
10. 作为这个服务的唯一用户，我想让判定在后台做、feed 立刻返回，这样 234 部的清单不会撞上 qBittorrent 30 秒无字节就掐断的硬限。
11. 作为这个服务的唯一用户，我想让判定循环限速在 100 个种子/小时以内，这样我不会因为撞上站点的建议速率而给账号找麻烦。
12. 作为这个服务的唯一用户，我想让判定循环可续跑（重启从「没有判定的作品」继续），这样回填不必从头再来。
13. 作为这个服务的唯一用户，我想让循环周期由配置给、`SIGHUP` 可改、`0` 关闭，这样它和健康探针是同一套操作习惯。
14. 作为这个服务的唯一用户，我想让 feed 条目的 `guid` 仍然是 infohash，这样同一部作品同时出现在想看和别的订阅里时 qBittorrent 只下一次。
15. 作为这个服务的唯一用户，我想让 M-Team 条目的 `guid` 由**内容**决定（而不是馒头数据库里的一个外键），这样馒头重建一个种子不会让 qBittorrent 当成新内容再下一份。
16. 作为这个服务的唯一用户，我想让 M-Team 条目交出的是**种子文件**而不是磁力，这样私种能真的连上 tracker（裸磁力是死链）。
17. 作为这个服务的唯一用户，我想让那个种子文件由本服务端出（而不是馒头的临时链接），这样我拿到的东西不会 5 分钟后过期。
18. 作为这个服务的唯一用户，我想让 `feed.base_url` 决定那个种子的地址，这样集群里 qBittorrent 能用集群内的名字取到它。
19. 作为这个服务的唯一用户，我想让来源一经下发就冻结，这样已下过的东西不会因为馒头后来有了而静默变成第二份。
20. 作为这个服务的唯一用户，我想让「重置」是唯一的换源出口（删判定 + 删钉住 + HUP），这样换源是一个**我动手做**的动作，而不是一个悄悄发生的事。
21. 作为这个服务的唯一用户，我想让重置之后日志里有一条 WARN 说明「这次切换会导致重新下载」，这样我知道自己刚刚付了什么代价。
22. 作为这个服务的唯一用户，我想让 M-Team 的中文字幕判定只依据上游给的标签，这样服务不会去猜文件名。
23. 作为这个服务的唯一用户，我想让槽位规则在 M-Team 的那一组候选内部照常生效（中文字幕优先、再看时间），这样命中时也不会拿一个更差的版本。
24. 作为这个服务的唯一用户，我想让「番号命中」是精确的（番号必须作为独立词元出现），这样服务不会把别的片当成本作品发给我。
25. 作为这个服务的唯一用户，我想让 M-Team 的凭据失效（key 过期/被换）在日志、`/healthz/upstream` 与 `/metrics` 上**单独成一类**，这样我不会把它当成「上游坏了」去重启。
26. 作为这个服务的唯一用户，我想让 `/metrics` 出判定状态（已判定/命中/待判定/上次判定时间），这样我能看见回填在推进。
27. 作为这个服务的唯一用户，我想让判定停滞（连续若干轮没有推进）看得见，这样「看起来在工作、实际没在工作」不会长期藏着。
28. 作为这个服务的唯一用户，我想让 README 明说「本服务发出的种子带着你的账号凭据，而本服务不做鉴权」，这样我知道它的暴露面比现状严重一档。
29. 作为这个服务的唯一用户，我想让 README 明说「轮换 M-Team 密钥后已发出的种子会全部失效、且本服务看不见也修不了」，这样那一天到来时我知道该做什么。
30. 作为这个服务的唯一用户，我想让判定表损坏或版本不认识时服务**拒绝启动**，这样它不会用一张空表静默覆盖我的状态。
31. 作为这个服务的唯一用户，我想让判定表与 pin 放在**不同的文件**里，这样我能一眼看出「哪个丢了会出事、哪个丢了只是重查」。
32. 作为这个服务的唯一用户，我想让 M-Team 的开关只是「配没配 key」，这样我不必再理解第二个开关。
33. 作为这个服务的唯一用户，我想让 `MTEAM_API_KEY` 环境变量优先于配置文件，这样集群里凭据走 Secret、和 `JAVDB_TOKEN` 是同一套。
34. 作为这个服务的唯一用户，我想让三份部署配置的键集合始终一致，这样我不会只在某一种部署上踩空。
35. 作为这个服务的唯一用户，我想让新状态目录在三套部署里都可写（照 pin 那一节的做法），这样升级后服务不会拒绝启动。
36. 作为这个服务的唯一用户，我想让判定循环读不到想看清单（没 token / 上游坏）时跳过本轮而不是退出进程，这样一次抖动不会变成重启循环。
37. 作为这个服务的唯一用户，我想让 M-Team 的 User-Agent 是显式设置的，这样 Cloudflare 不会因为 `curl/*` 或空 UA 把我 302 到 google（那看起来像鉴权失败）。
38. 作为这个服务的唯一用户，我想让 M-Team 的请求体编码按端点分别正确，这样 `detail` / `genDlToken` 不会因为给了 JSON 而返回 `參數錯誤`。
39. 作为这个服务的唯一用户，我想让 `/torrent/{infohash}.torrent` 对不认识的 infohash 返回 404（而不是 500 或空文件），这样排错时一眼能看出是「没有」还是「坏了」。
40. 作为这个服务的唯一用户，我想让「想看」清单被清空时 feed 退化成一张空表而不报错，这样这份**待办队列**的日常增删不会打断服务。

## Implementation Decisions

**两个数据来源。** 上游仍是 JavDB App 的私有 API（`/api/v1/...`），一个字不改。
M-Team 是第二个来源，通过 `x-api-key` 的 REST 接口访问。`CONTEXT.md` 里「上游」这个词
**从此特指第一个**；要泛指两者时说「数据来源」。这个区分有后果：上游的故障进 `/readyz`，
而 M-Team 的凭据失效**不该**进（换 key 不是重启能解决的）。

**准入与范围。** 一部作品走不走 M-Team，取决于**它在不在 App 的想看清单里** ——
不是 URL 里的番号，也不是配置里的白名单（用户只会在 App 里点它）。生效范围**只有
`/rss/want.xml` 一条路由**：想看清单里的作品按定义就是这条 feed 的内容，在别处再查一遍
没有新信息；而把 M-Team 铺到所有 feed 上会让「判定未就绪就扣住」传染到女优订阅，
使那条 feed 的内容取决于馒头通不通。

**领域模型：候选带来源。** 磁链候选现在有两个来源，因此它要记住自己来自哪个：

```
type MagnetSource uint8      // 零值必须是上游 —— 既有构造点不必改
const (
    SourceUpstream MagnetSource = iota
    SourceMTeam
)
```

⚠️ 实现时改过一个字：类型叫 `MagnetSource` 而不是 `Source` —— 后者在本包里已经被
`catalog.Source`（端口接口）占了。两个东西层次不同（一个是「候选从哪来」，
一个是「数据从哪取」），但同名会很难读。

`catalog.Magnet` 增加 `Source` 字段（零值 = 上游）。`catalog.Work` 不变。

**交付物：`guid` 仍是 infohash，enclosure 换成种子 URL。** `feed.Item` 按
`Magnet.Source` 决定 enclosure：上游 → 磁链（现状，一字不改）；M-Team → 本服务的
`GET /torrent/{infohash}.torrent`，`type` 仍是 `application/x-bittorrent`
（qBittorrent 只认这个值；空 type 会落到备选字段，别的值直接忽略）。
`GUID()` 不变。理由与代价见 ADR-0004。

**判定有三种结果，语义完全不同。**

| 结果 | 含义 | 会不会再问 |
|---|---|---|
| 命中 | 馒头有，候选快照与选中的那条（含 infohash 与种子字节）都已取回 | 不再问 |
| 负结果 | 查过，馒头没有 | **永不**再问 |
| 查询失败 | **没查成**（网络 / 限流 / 凭据） | 不自动重试；只有「重置」会再试 |

**判定表是第二份持久状态，且刻意与 pin 不同构。** 独立文件、`0600`、flock 单写者、
损坏或版本不认识 ⇒ **拒绝启动**、落盘失败 ⇒ 致命（四条都照 `pin.Store` 的先例）。
与 pin 的区别要写在包注释里：**丢判定表不会改 `guid`**（pin 还在），代价是重查一遍；
丢 pin 会让客户端静默重复下载。这正是它们不放在同一个文件里的理由。

**来源优先 = 整体换池，不是合并池。** 命中时该作品的候选池**整体换成** M-Team 的那一组
（首次查询时的快照），上游的候选被丢弃。槽位规则本身一字不改，但它**只在一个来源之内适用**：
两边的 `created_at` 不同源（上游是 `09/27/2026` 这种天粒度，M-Team 是
`2021-02-22 15:19:51` 这种秒粒度、且表示「上传到馒头的时间」），合并之后「取最新」
会因为一个与质量无关的字段判胜。

**首发冻结落在 M-Team 层，不落在 pin 里。** M-Team 装饰器坐在 `pin` **外面**
（先于 pin 执行）并**读** pin 表：这部作品已有钉住 ⇒ 一律不动，连问都不问。
没有钉住 ⇒ 有命中就把候选池换掉，然后由 pin 照常钉住它选中的那条。
**不新增 `pin.json` 的字段** —— 动那份 schema 是这个仓库最贵的一类改动，
而收益只是措辞更集中。`pin.Store.Get` 已经存在，不需要新的读接缝。

**装配顺序。** 新装饰器插在既有链里，保持「`dedupe` 最外、`pin` 在里」这条既有的正确性约束
（`dedupe` 把同一个切片交给所有调用者，`pin` 会原地改写它）。M-Team 装饰器同样会原地改写，
因此它也必须在 `dedupe` 之内。

**判定循环。** 常驻 goroutine，照 `health.Run` 的形状：周期由配置给、`SIGHUP` 可改、
`0` 表示关闭。它读想看清单 → 对**没有判定**的作品查 M-Team → 写判定表。
限速：种子下载不超过 **100 个/小时**（站点建议值）。可续跑：判定表就是进度。
读清单失败 ⇒ 跳过本轮 + WARN，**不退出进程**。

**扣住未就绪。** 只有「尚未判定 / 正在判定」才扣住；`负结果` 与 `查询失败` **不扣**
（按上游下发并钉住）。计数与既有的「待磁链」**同源**，由 `wantSummary` 一处构造，
同时写进 channel 标题与描述（qBittorrent 只呈现标题，描述留给会读它的人）。

**M-Team 客户端的契约**（全部实测过，见 notes）：

- base `https://api.m-team.cc`，一律 POST，鉴权头 `x-api-key`，成功判据 `message == "SUCCESS"`
- **User-Agent 必须显式设置、非空、且不含 `curl`** —— 否则 Cloudflare 会 302 到 `www.google.com`，
  那**不是**鉴权失败，要单独成一类错误
- **请求体编码按端点分**：搜索用 JSON，`detail` 与 `genDlToken` 用 form/multipart
- 三类「重试无用」的错误要能被上层判定：凭据无效、UA 被拦、下载链接过期
  （`code=1` / `連結不可用！ 超出有效期`）
- `mode` 固定 `adult`，不做 normal 区 fallback
- 中文字幕**只信搜索返回的 `labelsNew` 里含 `中字`** —— 不要读 `detail` 的
  `hasChineseSubtitle`（实测它在有「中字」标签时仍是 `false`）
- `createdDate` 是 `"2021-02-22 15:19:51"`（秒粒度字符串），不是时间戳

**bencode → infohash。** 对 `info` 字典的**原始字节切片**取 SHA-1，不重新编码
（重新编码要求编码器逐字节复现原始的所有选择；错了会得到一个语法合法但错误的 infohash，
而它会直接变成 `guid`，**没有任何外部信号**）。只认 v1；只有 v2 时**拒绝并报错**。
同时校验 `announce` 里带凭据（形状：`https://tra1.m-team.cc/announce?credential=<base64>`，
解开是 `sign=&t=&tid=&uid=`；**不是 `passkey=`**），不带就报错 —— 那种种子在客户端是红种、
在我们这边无声。

**番号匹配。** 判据是「番号两侧不是字母数字」，写成正则
`(?<![A-Za-z0-9])SONE[\s\-_]*168(?![A-Za-z0-9])`（分隔符允许 `-`/`_`/空格/相连）。
⚠️ **不能**写成「按非字母数字切词再比词元」—— 日文汉字会把 `SONE-168` 切成
`SONE` + `168`，于是一条都匹配不上，表现为「馒头没有」。

**配置。** `mteam.api_key`；环境变量 `MTEAM_API_KEY` 优先，**空值不算「设置了」**
（照 `JAVDB_TOKEN` 那条既有判断）。三份部署配置的键集合仍由
`internal/config/examples_sync_test.go` 强制一致。**没有第二个开关** ——
「配没配 key」就是开关。

**种子字节存下来。** 判定表同目录下的 `torrents/`，权限 `0600`（里面有账号凭据）。
理由：凭据**长期有效**（用户观测：几个月前加的种子仍正常汇报），因此存下来是安全的，
而且让「客户端取种子」只依赖本服务、不依赖馒头。
**残余风险（必须写进 README）**：凭据绑账号 ⇒ 用户轮换密钥后已发出的种子会全部失效，
而本服务既看不见也修不了；唯一出口是逐部「重置」，代价是重复下载。

**重置。** 删掉该作品的判定条目与 pin 条目 + `kill -HUP` 重读。下一次渲染会重新判定，
并**允许换来源**（可能重复下载一份，日志打 WARN）。沿用 README 里已有的
「删掉某一条 pin + HUP」这个操作习惯，只是从删一处变成删两处。

## Testing Decisions

**什么算好测试**：只断言外部行为。本仓库的既有口味是——装饰器只断言「它对
`catalog.Source` 的返回值做了什么改写」，纯函数只断言输入到输出的映射，持久状态只断言
「文件里留下什么 / 坏文件会怎样」，HTTP 只断言状态码与正文。**不断言内部函数被调用了几次、
不断言私有字段**（既有的 `fakeSource.calls` 是个例外，它数的是**上游被打了多少次**，
那是对外可见的成本，不是实现细节）。

**三处接缝，全是既有的，不新开：**

| 接缝 | 断言什么 | 先例 |
|---|---|---|
| **HTTP mux（主）** | 全部用户可见行为：`<guid>`、`<enclosure>` 的 URL 与 `type`、channel 标题里的两个计数、`/torrent/{infohash}.torrent` 的字节与 404。用可编程的 `catalog.Source` + `httptest` 假 M-Team | `internal/httpapi/server_test.go`、`internal/feed/rss_test.go` |
| **判定表自己的测试** | 外部看不见的那件事：损坏 / 版本不认识 ⇒ 拒绝启动；flock 单写者；三种结果的读写往返 | `internal/pin/store_test.go` |
| **纯函数** | bencode→infohash（错了没有任何外部信号，需要**外部来源**的期望值夹具）；`feed.Item` 的 enclosure 选择（表驱动，逐字钉住 XML） | `internal/catalog/select_test.go`、`internal/feed/rss_test.go` |

**M-Team 的 HTTP 边界不是接缝，是测试替身**（`httptest`），与 `internal/appapi` 的既有做法一致。
判定循环用**真实的短周期**驱动（照 `internal/health/health_test.go` 的做法），不引入假时钟 ——
本仓库没有假时钟，`health.Run` 的 `interval func() time.Duration` 就是它的注入点。

**票 01 的测试**：`feed` 的表驱动测试里新增「种子 URL」那一支；既有全部用例的 XML
必须**逐字节不变**（这是「行为零变化」的判据）。

## Out of Scope

- **主动推送模式**（推给 qBittorrent + 回写「看过」）—— 形状已定在
  `.scratch/javdb-rss/notes/want-push-deferred.md`，本轮不碰
- **除 `/rss/want.xml` 之外的 feed 上的 M-Team**（见 Implementation Decisions）
- **normal 区的 fallback**（`mode` 固定 `adult`）
- **磁力**：不合成磁链、不做 tracker 中转（理由见 ADR-0004 的 Considered Options）
- **M-Team 候选池的定期重查** —— 池子冻结在首次查询，所以馒头后来补的中字版看不见。
  这与「负结果永久」是同一条取舍
- **`/torrent/` 端点的防枚举**（路径里是裸 infohash，而它就在 feed 的 `<guid>` 里，
  收益接近零；真要挡得挡在服务鉴权上，那是整个服务的立场问题）
- **判定表的淘汰**（234 部 ≈ 10–25MB，目前不做）
- **多实例**（照 pin 的立场：单写者，第二个实例拒绝启动）
- **宽泛的仪表化**（请求量、耗时直方图等）
