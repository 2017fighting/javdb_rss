# javdb-rss · M-Team 优先

一句话：**你在 App 里标了「想看」的作品，如果馒头上也有，就用馒头那一份。**

这一轮的终点不是「支持多站点」——是**一件事**：几年前的老片，JavDB 上的磁链慢得
下不动，而馒头上很快。用户的原话是「M-Team 只是用来解决这个问题的」。
因此下面每一条保守的选择，都是从这句话推出来的 —— 它**不是**「M-Team 是更好的来源」，
而是「M-Team 是少数老片的更快的镜像，而它既不如 JavDB 新、也不如 JavDB 全」。

> 读票之前先读本文的 Decisions so far —— 票面只说「还剩什么要做」，
> 地图说「为什么这么定、否掉了什么」。

## 三条硬约束（整个形状是被它们逼出来的）

1. **`/rss/want.xml` 已经很慢了。** 实测 234 部 = 24 页清单 + 222 次磁链请求 ≈ **20 秒/次渲染**
   （`README.md` 的「想看」一节，`app_api.magnet_concurrency` 默认 8）。
   当前清单只有 **5 部**（2026-10-13 实测），但它是**待办队列**、会被填回几百部 ——
   所以按最坏情况设计，不能按当前那 5 部设计。
2. **qBittorrent 在 30 秒无字节传输时掐断请求**（Qt 默认；`downloadmanager.cpp:336`
   是无参的 `setTransferTimeout()`）。而 feed 是渲染完才写第一个字节。
   ⇒ **同步做 M-Team 判定（234 次搜索 + 最多 234 次种子下载）不可能**，那是分钟级。
3. **M-Team 的种子下载速率是 100 个/小时**（站点自标的建议值，见 `notes/mteam-api.md`）。
   回填 234 部、若多数命中 ⇒ **至少 2.3 小时**。

再加一条本仓库自己的性质：**pin 在首次渲染时就落地**。配上「永不自动换来源」，
判定必须在**首次下发之前**就绪 —— 否则整张清单在第一次轮询时就被冻结在 JavDB 上，
功能等于没做。

⇒ 形状只能是：**判定在后台常驻 goroutine 里做，限速、可续跑；feed 只读判定结果。**

## 两条会让人白折腾半天的 API 坑（都实测过，写在这里免得重踩）

1. **`curl/*` 与空 User-Agent 会被 Cloudflare 302 到 `www.google.com`** ——
   看起来像「key 无效」或「被墙」，其实是 WAF 按 UA 拦的。
   `Go-http-client` / `python-requests` / `Wget` / 任意自定义 UA 都放行。
   ⇒ 实现里显式设一个非空 UA，**并把那个 302 认成独立的一类错误**（票 01/07）。
2. **请求体编码不统一**：`search` 要 JSON，`detail` 与 `genDlToken` 要 **form/multipart**
   （给 JSON 一律 `message="參數錯誤"`）。站点自己的 wiki 就说文档的 json/form 不可信。

## Decisions so far

- **准入 = 「这部作品在你的 App 想看清单里」。** 不是 `feeds.codes` 白名单，也不是
  「URL 里的番号」。理由有两条，第一条是用户的原话：**「我怎么会手动改这个配置文件，
  我只会在 javdb app 上将某个番号加入想看」** —— 准入条件必须落在用户真正会做的那个
  动作上。第二条是副作用：这个服务不做鉴权，若准入是「URL 里的番号」，任何能访问到
  它的人都能枚举 `/rss/code/AAAA-001.xml`，每次未命中烧掉一次 M-Team 搜索
  （1000 次/24h）并拿账号去撞馒头的接口。落在 App 清单上，这条攻击面直接不存在。
  **否掉的**：① `feeds.codes` 白名单（要用户手改配置，而他明确不会）；②
  「任何 URL 里的番号」（上面的滥用面）；③ 顺带**否掉了 `/rss/want.xml` 之外的
  准入形态** —— 见下一条。

- ⚠️ **生效范围 = 只在 `/rss/want.xml` 上。这一条是从上面那条 + 「女优 feed 完全不查」
  推导的，不是单独问过的。** 想看清单里的作品**按定义**就是这条 feed 的内容，所以
  在别处再查一遍没有新信息。**代价照实记**：一部作品若先被别的 feed（女优 / 清单 /
  标签 / 番号）下发过，pin 已存在 ⇒ 按「首发冻结」它永远不会走 M-Team，哪怕你后来
  把它标成想看。出口是**重置**（见下）。不这么选的代价更大：把 M-Team 铺到所有 feed 上，
  「判定未就绪就扣住」会**传染**到女优 feed —— 那条 feed 的内容从此取决于馒头通不通，
  而它现在只受自己的上游影响。

- **来源优先，不是合并池。** M-Team 命中 ⇒ 该作品的候选池**整体换成** M-Team 的那一组
  （首次查询时的快照），JavDB 的候选被丢弃；M-Team 无命中才用 JavDB。
  **否掉的**：把两边候选并成一个池子用同一条槽位规则选。除了「优先」二字会失去含义，
  它还有个具体的技术脏处：两边的 `created_at` 不同源（JavDB 是天粒度的 `09/27/2026`，
  M-Team 是 `2021-02-22 15:19:51` 这种秒粒度），而 M-Team 的 `createdDate` 是**上传到馒头的时间** —— 老片在
  馒头上的上传时间总是很新，于是「取最新」会**因为一个与质量无关的字段**把 M-Team 判胜。
  结果碰巧对，理由是错的。

- **命中判定 = 归一化后的番号必须作为独立词元出现在种子名里。** 去掉连字符与空格、
  统一大小写、容忍 `-C` / `-U` / `4K` 之类前后缀，但番号整体要匹配一个词元。
  **否掉的**：宽松子串（`328` 也认 —— 短番号上误配率高）；只信馒头的番号元数据接口
  （多一层未验证的依赖，收益不明确）。搜出多条命中按常态处理（在 M-Team 内部按槽位
  规则选一条），**不做交互式消歧** —— 这是无人值守的 RSS。
  ✅ **实测（2026-10-13，用户真实想看清单 5 部）：4 部命中（80%），严格匹配零误配。**
  命中里多数有一条带中字版，所以「来源优先」不必然丢掉中文字幕。
  ⚠️ **判据的实现有个坑**：「按非字母数字切词再比词元」是**错的** —— 日文汉字会把
  `SONE-168` 切成 `SONE` + `168`，于是一条都匹配不上（我第一版就写错了，
  表现为「馒头没有」，而其实是判据坏了）。正确形式是正则
  `(?<![A-Za-z0-9])SONE[\s\-_]*168(?![A-Za-z0-9])`。

- **不发磁力。`guid` 仍是 infohash。** `<enclosure>` 指向本服务的
  `GET /torrent/{infohash}.torrent`（`type="application/x-bittorrent"`）。
  ⭐ 关键事实：qBittorrent 里 **`guid` 与 `enclosure` 是两回事** ——
  `rss_parser.cpp` 分别解析（`:649` / `:622`），去重只看 `articleByGUID()`
  （`rss_feed.cpp:203`），而 `enclosure` 只是「去哪儿拿种子」；
  `Article::isSupportedTorrentURL()` 接受 `http(s):` 与 `magnet:`（`rss_article.cpp:125`）。
  所以「保住 guid = infohash」和「发种子文件而不是磁力」可以同时成立。
  为什么不用磁力：**M-Team 是私种，裸磁力是死链**（announce 里那份按次签发的凭据
  只存在于 `.torrent` 里），而合成一条带真 announce 的磁力，feed 里就带凭据、
  且没法验证客户端能否取到 metadata。理由与代价的完整账在
  [`docs/adr/0004`](../../docs/adr/0004-mteam-guid-is-infohash.md)。
  **否掉的**：① 交馒头自己的 `genDlToken` 链接（✅ 实测：那条链接约 5 分钟就失效，
  而 qbt 是稍后才取的 —— 这条路是死的）；② 合成磁力 `tr=` 指向真 tracker（feed 带凭据）；
  ③ 合成磁力 `tr=` 指向本服务做中转（**tracker 只给 peer 地址、不给 metadata，
  所以它修不了「取不到 metadata」**；它唯一买到的是隐藏凭据，代价是把那条 `tr`
  永久写进客户端，本服务停机或换端口 = 所有已发出的种子停止 announce）。

- **判定在后台常驻 goroutine 里做**（照 `health.Run` 的形状；`notes/want-push-deferred.md`
  里已经定过「进程内常驻 goroutine，周期由配置给、SIGHUP 可改」）。**feed 只读判定结果，
  绝不阻塞渲染** —— 理由就是上面那两条硬约束（20s 已用掉 30s 的三分之二）。
  限速：种子下载不超过 **100 个/小时**（站点建议值）。可续跑：重启不丢进度。

- **判定未就绪 ⇒ 扣住不发，但把计数写进 channel 标题**：
  `JavDB · 想看（234 部 · 12 部待磁链 · 37 部待定来源）`。
  这不是新概念 —— 它就是 want.xml 已有的那条惯用法（「尚无磁链的作品不发条目，
  但两个计数写进标题」，因为 **qBittorrent 拿不到 channel description**，
  它只呈现标题）。**否掉的**：先按 JavDB 下发（在「首发冻结」之下，第一次轮询就把整张
  清单冻在 JavDB 上，功能等于没做）；先按 JavDB 下发、判定落地后允许切换（回填期的
  重复下载是**批量**的，几十上百份，而不是偶尔一份 —— 正是「首发冻结」要避免的东西）。
  **代价照实记**：首次回填要几小时（100 个/小时），期间这些作品不在 feed 里。
  稳态没问题：新加一部，一个轮询周期内判定完（1 次搜索 + 1 次下载 ≈ 1–2 秒）。

- **负结果永久；查询失败不算负结果。** 「查过、馒头没有」是**永久判决**，不会因为
  「也许以后有了」而重查（用户的原话：新种子 javdb 有、mteam 没有 ⇒ 固定返回 javdb，
  之后也不会返回 mteam）。而「没查成」（网络 / 限流 / 401）**不构成判决**，它带一个
  可重试标记，但**不自动重试** —— 自动重试会在上游抖动时引发切换，也就是重复下载。
  两者的区别是刻意的：**「永久」的含义是「我查过并得到了答案」，不是「某天上游抖了一下」。**

- **首发冻结：来源永不自动更换。** 一部作品一旦以某个来源下发过，就不再换来源 ——
  M-Team 只可能出现在**首次**下发。**出口是「重置」**：手工把一部作品退回「尚未下发」
  （同时删掉判定条目与 pin 条目，`kill -HUP` 重读），下一次判定并**允许切换**
  （会重复下载一份，日志打 WARN）。这沿用 README 现有的「删掉某一条 pin + HUP」习惯，
  只是从删一处变成删两处。
  ⭐ 这条出口是必需的，不是可选的：没有它，「永不自动切换」会变成「永不切换」，
  于是一次上游抖动就让那部作品**永久**失去这个功能，而且失效是静默的 ——
  正是本项目一直在消灭的那类失败。

- **想看里 JavDB 尚无磁链的作品，也查 M-Team。** 这一类恰恰是 M-Team 最该救的：
  老片，JavDB 上至今没人传（就是标题里「待磁链」的那一拨），而馒头上早就有。
  之前一度定的是「只在 JavDB 有磁链时才查」，理由是「mteam 没 javdb 新也没 javdb 全」——
  那条理由在「准入 = 番号订阅」时成立（「JavDB 有磁链」是个合理的兴趣信号），
  但准入改成「你自己标了想看」之后它就不成立了：**想看已经是最强的兴趣信号，
  没有理由再用 JavDB 的磁链状态去二次筛它。** 多花的是搜索配额（234 部只占 1000/24h 的 1/4）。

- **种子字节存下来，端点只负责发它。**（✅ 2026-10-13 定）客户端取种子只依赖本服务，
  不依赖馒头 —— 这与「本服务自己发种子」的初衷一致。凭据**长期有效**：
  用户观测，qBittorrent 里几个月前加的馒头种子现在仍正常汇报（凭据按次签发，
  但 tracker 不按时效验它；否则全站种子都会红）。
  ⚠️ **残余风险（已写进 ADR-0004，也要写进 README）**：凭据绑账号 ——
  **用户轮换 M-Team 密钥后，已存下的种子全部会死，而本服务既看不见也修不了**
  （唯一出口是逐部「重置」，而那会换 `guid`、重复下载）。
  即：**密钥轮换 = 一次（有界的）重复下载。**
  **否掉的**：「每次现取」（凭据永远新鲜、也能自然熬过密钥轮换，且省 10–25MB；
  但把「客户端取种子」变成同时依赖本服务与馒头都在线 —— RSS 本来就在定时轮询，
  让每一次取件都多一个可坏的外部环节，不划算）。

- **凭据的暴露面：接受。** 本服务发出的 `.torrent` 里带着一份账号维度的 tracker 凭据，
  而本服务不做鉴权 —— 谁能访问它，谁就能拿到它。隔离由 k8s 集群内 Service
  （qBittorrent 就在同一个集群）与 edge 的 authelia 提供。**这一条要写进 README 最显眼处**：
  它比现状「能看到你的订阅内容」严重一档。
  （⚠️ 第一版把这件事写成「passkey 暴露」—— 实测馒头已经不用 `passkey=` 了，
  现在是按次签发的 `credential=`；暴露的性质相同，但名字得对。）

- **`mode` 固定 `adult`**，不做 normal 区 fallback（先验证成人区真能搜到 AV 样本；
  搜不到再回来讨论）。**配置**：`mteam.api_key` + 环境变量 `MTEAM_API_KEY`（env 优先，
  照 `JAVDB_TOKEN` 的形状），三份部署配置的键集合仍由
  `internal/config/examples_sync_test.go` 强制一致。

- **判定搬出请求路径（票 04）。** `mteam.Source` 变成**只读**（应用判定 + 扣住未就绪），
  写者是后台的 `mteam.Loop`（限速 100 个种子/小时、可续跑、不退出进程）。
  未判定的作品**扣住不发**，但计数写进 channel 标题 —— 静默扣住就是静默少给数据。
  理由不是审美：订阅渲染已经接近 qBittorrent 掐断请求的时限（30 秒无字节传输），
  而一次判定要「搜索 + 下载种子」。

- ⚠️ **反转：「首发冻结」落在 `pin` 的**策略**里（票 09 + [`docs/adr/0005`](../../docs/adr/0005-first-emission-freeze-lives-in-the-policy.md)）。**
  最初定的是「落在 M-Team 层，**不新增 `pin.json` 的字段**」，理由是「收益只是措辞更集中」。
  **真实验收推翻了它**：真正决定最终发哪条的是 `pin` 的策略，而它只有在知道来源的
  前提下才可能尊重来源 —— 没有那一位，M-Team 层「原样放行」上游那个候选池会被策略
  判成「上游更好」，于是 pin 从馒头被换回上游（guid 抖回去 = 客户端多下一份，
  而且**馒头从此再也不生效**）。
  教训：判断「某条规则该落在哪一层」时，问的应该是**谁做最终决定**，
  而不是「哪一层加字段更便宜」。

- **验收结论（票 07，2026-10-14）**：真 key + 真 token + **真 qBittorrent v5.2.4**（Docker）
  走通 —— qbt 算出的 hash 与 feed 的 `<guid>` **逐位一致**、它真的解析了 feed
  （`rss/items` 里 guid = 馒头 infohash、torrentURL = 我们的种子地址）、
  guid 跨轮询与跨容器重建都不变、首屏 0.94s、回填 4 次下载。
  **仍未覆盖**：集群那份部署（k8s 清单 + PVC）与用户自己的 qbt —— 那条路已在
  `.scratch/javdb-rss-deploy/` 里单独验过。

- ⚠️ **一个反复出现的模式（值得记住）**：这一轮抓到 3 个 P0，**全都在装配层**
  （装饰器装配倒置 / 类型化 nil / 冻结不成立），而**前两个是测试比真实链路弱**
  （裸假 source 绕过「谁包谁」、字面 nil 绕过接口陷阱），**第三个只有真环境能抓到**
  （它只在第二次渲染现形，而所有测试都只渲染一次）。
  两轮评审还各自抓到一条**假阳性测试**（限速闸门从未被走到、目录穿越断言空转）。
  ⇒ 补了「真装配冒烟」（`TestBuildSourceWithMTeamUsesTheSecondSource` 真的驱动
  `loop.Once`）与「渲染两次」的钉子。

- **`/torrent/` 端点要不要防枚举**：现在路径里是裸 infohash，而 infohash 就在 feed 的
  `<guid>` 里 —— 所以「不可枚举」只挡得住「知道 infohash 但没拿到 feed」的人，收益接近零。
  真正要挡的话得挡在别处（服务鉴权），而那是整个服务的立场问题，不是这个端点的。
- **判定表的体积**：每部命中存一组候选快照 + 一个 `.torrent`（约 30–100KB）。
  234 部 ≈ 10–25MB。目前不做淘汰；若哪天想看清单长到几千部，再想。
- **`genDlToken` 本身算不算「下载种子」配额**：实测连调几次没有明显限流，未定。
- **M-Team 侧的中文字幕会不会后到**：本轮把 M-Team 的候选池**冻结在首次查询**，
  所以馒头后来补一个中字版，本服务看不见。这与「负结果永久」是同一条取舍
  （老片不会变），但它**确实**让既有的「出现中文字幕就切换」规则在 M-Team 作品上失效 ——
  如果用户在意，得改成「在 M-Team 内部按 TTL 重查」，那是配额账的另一个决定。
- **推送模式**（`notes/want-push-deferred.md`）：判定循环与它形状相同，但那是另一件事，
  本轮不碰。
