# 05: 重置 —— 唯一的换源出口

**What to build:** 手工把一部作品退回「尚未下发」：删掉它的判定条目与 pin 条目，
`kill -HUP` 重读。下一次渲染会重新判定，并**允许换来源**（因此可能重复下载一份，日志打 WARN）。

**没有它，「永不自动切换」会变成「永不切换」** —— 一次上游抖动或一次「当时馒头还没有」
就让那部作品**永久**失去这个功能，而且失效是静默的。

**Blocked by:** 02.

**Status:** resolved（2026-10-13）

      （只删一处不算：只删判定，pin 还在，来源仍被冻结）
- [x] 换源时日志有 **WARN**，说明这次切换会导致客户端重新下载一份

## Answer（2026-10-13）

**机制确认可用**：删掉两处（`mteam.json` 的 `verdicts` + `pin.json` 的 `pins`）+
`kill -HUP` ⇒ 后台重新判定 ⇒ **来源真的会换**。两条测试钉住它，并做了变异检验
（让 `handEdit` 变成空操作 ⇒ 两条当场响）。

⭐ **一处验收条目我做不到，订正在这里（不是含糊过去）**：

票面写着「换源时日志有 WARN」。但在「删两处」这个机制下，**服务观察不到手工重置** ——
删掉的那条 pin 就是唯一的证据，删完之后它眼里的这部作品与「第一次见到」一模一样
（走的是 `added` 分支，不是 `switched`）。两个表也没有单条删除的方法（重置就是手改 JSON），
所以也没有「删除钩子」可以挂。

于是我把 WARN 落在**服务真能看见的那件事**上：`pin` 被切换（guid 变了 ⇒ 客户端会多下一份），
并从 INFO 提到 **WARN**，文案写明后果。它覆盖的是「规则按设计换源」（例如上游出现中文字幕版），
而**重置那条提醒只能由文档给出** —— README 里已经改掉原来那句不成立的承诺，
并说明了为什么日志给不了。

**要让重置本身也被日志看见，只有两条路**（都不做，记在这里）：
1. **服务拥有重置操作**（HTTP 端点或子命令）—— 但 flock 是单写者，跑着的服务握着锁，
   子命令打不开；端点又要考虑本服务没有鉴权（多一个能触发重复下载的入口）。
2. **在 pin 里加一个「已重置」标记**（`"reset": true`）—— 循环据此重判、Source 据此换源，
   WARN 就能打出来。代价是运维要手改一个布尔值（比删两行更容易写错），
   而且给 `pin.json` 加字段是本仓库最贵的一类改动。

**测试**：`internal/mteam` 新增 2 条（`TestResetSwitchesTheSource` +
`TestResetNeedsBothEntriesDeleted` 的三个子情形：只删判定 / 只删 pin / 两处都删）。
后者钉的是最容易踩的那一步 —— 删了判定忘了删 pin，然后「换了 key 却什么都没发生」，
而没有任何地方会告诉他为什么。

**文档**：README 的「首发冻结，与『重置』」一节补上「这一步会让客户端重新下载一份」
以及**为什么服务端看不见它**。
