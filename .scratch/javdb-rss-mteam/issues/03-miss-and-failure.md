# 03: 判定的另外两种结果 —— 负结果与查询失败

**What to build:** 馒头没有 ⇒ **永久**负结果（照旧发上游那份，且不再重问）；
没查成 ⇒ 带可重试标记但**不自动重试**；凭据失效与「上游坏了」在日志、JSON、指标上分得开。

**Blocked by:** 02.

**Status:** ready-for-agent

- [ ] **负结果永久**：同一作品第二次渲染**不再打 M-Team**（有测试数上游被打了多少次）
- [ ] **查询失败不构成判决**：它不被写成负结果；带可重试标记与失败原因；**不自动重试**
- [ ] 三种结果（命中 / 负结果 / 查询失败）在判定表里是**可区分**的条目
- [ ] 「负结果」在日志与文案里**不写成「失败」** —— 那是另一回事，处置完全相反
- [ ] 凭据失效（401 / 无效 key）在 `/healthz/upstream` 的 JSON 里有一个**可判定字段**
      + `next_step`（自然语言，去控制台换 key），且**不**进 `/readyz`
      （照 `signature_broken` 的先例：重试无用的东西不该让人去重启）
- [ ] 「上游坏了」与「M-Team 凭据失效」是两条不同的日志消息
- [ ] 端到端：假 M-Team 分别返回空结果 / 401 / 网络错误 ⇒ 三种结果各自落地，feed 行为各自正确
- [ ] `make check` 与 `make race` 全绿
