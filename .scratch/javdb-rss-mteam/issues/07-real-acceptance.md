## Answer（2026-10-14）：Docker 验收结果

**环境**：真 key + 真 token + 真 M-Team + **真 qBittorrent v5.2.4**（Docker，
正是仓库笔记里验过的那个版本）+ state 走卷。本服务与本机用**本机构建的静态二进制**
跑在容器里（Dockerfile 的多阶段构建要拉 golang 镜像 + 下模块，本轮没走那条路）。

| 票面条目 | 结果 |
|---|---|
| 一部作品出现在 `/rss/want.xml`、enclosure 指向本服务 | ✅ 真的 5 部想看、4 个命中，enclosure 全是 `/torrent/<infohash>.torrent` |
| **qBittorrent 成功加上，且 infohash 与 guid 逐位一致** | ✅ qbt 算出的 hash = `e8556ddc…`，与 feed 的 `<guid>` **逐位相同**；任务名 `SONE-168-C.mp4` 正是馒头那份种子的 `info.name` |
| qbt 真的**解析**了这条 feed | ✅ `rss/items` 里 4 条，每条 `guid` = 馒头 infohash、`torrentURL` = 我们的种子地址；channel 标题里的计数它也读到了 |
| `guid` 跨轮询不变 | ✅ 三次连续渲染的 guid 集合 md5 逐位相同 |
| `guid` 跨容器重建不变 | ✅ 重启容器后仍相同；判定表仍 5 条（**不重查**） |
| 首屏仍在 30 秒内 | ✅ **0.94s** |
| 回填没有撞上建议速率 | ✅ 4 次下载（上限 100/小时） |

⚠️ **本轮验收抓到并修掉了一个 P0**（票 09）：**首发冻结不成立** —— 第二次渲染会把
M-Team 那条换回上游（guid 抖回去 = 客户端多下一份，而且馒头从此再也不生效）。
修完复验：三次渲染 enclosure 全部是 `/torrent/…`、guid 集合 md5 相同、
零条「pin 切换」WARN（修前 4 条）。

**仍未覆盖的（照实记）**：集群里那份部署（k8s 清单 + PVC）与**你自己的 qbt** 没被
这次验收覆盖 —— 那条路已在部署 effort 里单独验过，而本轮的结论是
「**服务本身在真 M-Team + 真 qBittorrent 上走通了**」。

⚠️ 另外一条真实教训（写进票 09 与 ADR-0005）：那个 P0 **躲过了 6 张票的全部测试**，
