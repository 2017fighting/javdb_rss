# 04: 规模 —— 判定挪到后台，未就绪的扣住

**What to build:** 判定移出请求路径（常驻循环、限速、可续跑），`/rss/want.xml` 只读结果、
立刻返回；判定**尚未就绪**的作品不发条目，但在 channel 标题里被计数。
判据是硬的：一个 200+ 部作品的清单，首屏必须仍在 **30 秒**内
（qBittorrent 在 30 秒无字节传输时就掐断请求，而 feed 是渲染完才写第一个字节）。

**Blocked by:** 02, 03.

**Status:** resolved（2026-10-13）

- [x] 常驻循环：周期由配置给、`SIGHUP` 可改、`0` 表示关闭（照 `health.Run` 的形状与语义）
- [x] **限速**：种子下载 ≤ **100 个/小时**（站点自标的建议值）
- [x] **可续跑**：判定表就是进度；重启后从「没有判定的作品」继续，**不重查**已判定的
- [x] 读想看清单失败（没 token / 上游坏）⇒ 跳过本轮 + WARN，**不退出进程**
      （退出会把一次抖动变成重启循环，而它没那么严重）
- [x] `/rss/want.xml` 的 handler **不发任何 M-Team 请求**（只读内存里的判定表）——
      这条要有测试守着，它是「首屏 < 30 秒」的根据
- [x] 未就绪（尚未判定 / 正在判定）⇒ **不发条目**，并计入标题与描述的「N 部待定来源」
- [x] **负结果与查询失败不扣**：它们按上游下发并钉住（查询失败的出口是「重置」，见票 05）
- [x] 「待定来源」与既有的「待磁链」**同源**（由 `wantSummary` 一处构造），
      不会一边说 12 部、一边说 13 部
- [x] 标题写法照既有惯例：**qBittorrent 只呈现 channel 标题**（它的 RSS API 响应里没有
      description 字段），所以计数必须进标题；描述里同时给完整句子
- [x] 端到端：一个 200+ 部作品的假清单，首屏 < 30 秒，且标题里的计数随时间**下降**
- [x] `make check` 与 `make race` 全绿

## Answer（2026-10-13）

**这是一次分工重切**，不只是加了个循环：

| | 之前（票 02/03） | 现在 |
|---|---|---|
| `mteam.Source` | 请求路径里查 M-Team（同步） | **只读**：应用判定 + 扣住未就绪 |
| `mteam.Loop` | 没有 | **写者**：查、限速、可续跑、落盘 |

⭐ **四处实现判断（记在这里）**：

1. **扣住的计数放在 `catalog.WantList.PendingSource`，而不是靠「Works 少了几条」去推。**
   少了几条无法区分「判定没就绪」与「清单缩水了」，而两者的处置完全不同。
   有它，标题才能把「N 部待定来源」说出来 —— 静默扣住就是静默少给数据。
   相应地 `wantSummary.total()` 改成 `len(Works) + PendingSource`：用户看到的是
   「我在 App 里标了几部」，而不是「服务这次愿意发几条」。

2. **限速闸门在「下载」那一步，不在循环外面。** 搜索是便宜的（1000/24h），
   下载才是瓶颈（100/h）。闸门关掉时**不写判定** —— 「还没取到种子」不是任何一种结果，
   写进去就等于「永久不再试」，而它明明只是等下一轮。

3. **闸门手写而不是引 `golang.org/x/time/rate`。** 本仓库对依赖的态度是「为它写过一张 ADR」
   （ADR-0003），而这里要的只是「一小时不超过 N 次」—— 一个环形时间戳队列就够了。
   它刻意是**滑动**窗口：整点清零会在整点前后各放行 N 个，也就是一小时里 2N 个。

4. **循环读的是 `client`（原始上游），不是包好的那层。** 包好的那层会把未判定的作品
   扣住，于是循环**永远看不到它们** —— 一个死锁。`buildSource` 因此多返回一个 `*mteam.Loop`。

**测试**：`internal/mteam` 新增/重写 12 条（请求路径零调用、命中换池、负结果与失败放行且不重问、
钉住不查、可续跑、限速、读清单失败不退出、`0` 关闭是真正的空操作、三种结果可区分、
认不出的结果要说一声、闸门是滑动窗口）+ `internal/httpapi` 2 条（扣住 + 标题计数；
240 部未判定清单首屏零 M-Team 调用）。

**变异检验**：把扣住的 `pending++` 去掉 → 三条测试当场响（含标题里那个计数）。

⚠️ **仍未做（照实记）**：票面那条「端到端：200+ 部清单首屏 < 30 秒」我没有做**墙钟断言** ——
CI 上的墙钟断言很脆。改成断言「handler 一次 M-Team 都没打」，而那正是首屏快的原因。
