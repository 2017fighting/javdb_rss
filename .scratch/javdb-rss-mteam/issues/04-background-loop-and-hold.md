# 04: 规模 —— 判定挪到后台，未就绪的扣住

**What to build:** 判定移出请求路径（常驻循环、限速、可续跑），`/rss/want.xml` 只读结果、
立刻返回；判定**尚未就绪**的作品不发条目，但在 channel 标题里被计数。
判据是硬的：一个 200+ 部作品的清单，首屏必须仍在 **30 秒**内
（qBittorrent 在 30 秒无字节传输时就掐断请求，而 feed 是渲染完才写第一个字节）。

**Blocked by:** 02, 03.

**Status:** ready-for-agent

- [ ] 常驻循环：周期由配置给、`SIGHUP` 可改、`0` 表示关闭（照 `health.Run` 的形状与语义）
- [ ] **限速**：种子下载 ≤ **100 个/小时**（站点自标的建议值）
- [ ] **可续跑**：判定表就是进度；重启后从「没有判定的作品」继续，**不重查**已判定的
- [ ] 读想看清单失败（没 token / 上游坏）⇒ 跳过本轮 + WARN，**不退出进程**
      （退出会把一次抖动变成重启循环，而它没那么严重）
- [ ] `/rss/want.xml` 的 handler **不发任何 M-Team 请求**（只读内存里的判定表）——
      这条要有测试守着，它是「首屏 < 30 秒」的根据
- [ ] 未就绪（尚未判定 / 正在判定）⇒ **不发条目**，并计入标题与描述的「N 部待定来源」
- [ ] **负结果与查询失败不扣**：它们按上游下发并钉住（查询失败的出口是「重置」，见票 05）
- [ ] 「待定来源」与既有的「待磁链」**同源**（由 `wantSummary` 一处构造），
      不会一边说 12 部、一边说 13 部
- [ ] 标题写法照既有惯例：**qBittorrent 只呈现 channel 标题**（它的 RSS API 响应里没有
      description 字段），所以计数必须进标题；描述里同时给完整句子
- [ ] 端到端：一个 200+ 部作品的假清单，首屏 < 30 秒，且标题里的计数随时间**下降**
- [ ] `make check` 与 `make race` 全绿
