## Answer（2026-10-13）

**落点**：`mteam.Store.Stats()`（一次拿全的计数快照）、`mteam.Loop.Progress()`
（轮数 / 待判定 / 停滞 / 上次一轮时刻）、`httpapi.mteamCollector`（投影成指标）、
`Loop.recordFailure` 的**翻转式**日志、以及「凭据失效立刻停轮」。

⭐ **四处判断（记在这里）**：

1. **`judged` 必须单独成一条。** 一条判定都没有时三个 `verdicts` 全是 0 ——
   那与「判定过、三个结果都是 0」在**计数**上完全一样。这与 `/metrics` 里
   `checked` 那条既有判断同构，也是票面点名要的那件事。
2. **时间戳与 `pending_works` 在「从未」时不出现**（不是报 0）—— 报 0 等于说
   「1970 年判定过」或「跑过且没有欠账」，而 staleness 类规则正是拿它算的。
3. **凭据失效立刻停轮。** 原实现里一个坏 key 会把整张清单一条条撞同一个错 ——
   既白烧搜索配额，又把日志刷满。现在停在第一部，并**只在状态翻转时**打一条 ERROR
   （照 health 的做法）。这是票面那条「日志只在翻转时打」真正咬到的地方。
4. **`Stats` 一次拿全**，而不是让调用方逐个方法去问：后者会让「命中数」与「总数」
   在两次调用之间被改掉，于是指标里出现 `h+m+f ≠ total` 这种自相矛盾的读数。

**测试**：`internal/httpapi` 4 条（没配就没有序列 / 从未判定 vs 判定过且为 0 /
进度与凭据 / 从未跑过时不报 pending）+ `internal/mteam` 2 条（凭据失效停轮且只打一次 /
停滞计数）。两条新的循环测试都做了**变异检验**（把停轮判断与停滞判断分别去掉 ⇒ 当场响）。

**票面的 README 那条已经在票 08 做完了**（那四件事：怎么开、怎么重置、凭据暴露面、
密钥轮换的后果、回填是渐进的 —— 都在 `## M-Team 优先（可选）` 那一节里）。
本票另外把**新增的那组指标**写进了 README 的 `/metrics` 一节，并给出了一条可用的
停滞告警表达式。
