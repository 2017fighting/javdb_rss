# 女优订阅的参数表

`GET /rss/actress/{id}.xml?<参数>` 里各参数的权威说明。

**每一条都是对着真实上游实测得到的**（2026-09-30 首测，2026-10-01 由 ticket 03
复勘并补上先前标为「未验证」的部分），不是从文档或先例项目抄的 ——
上游没有公开文档，而先例项目在几处细节上与实测不符（见文末「与先例项目的出入」）。

## 参数分两类

这是最容易搞混的一处，所以先分清：

| 类别 | 参数 | 谁在用 |
|---|---|---|
| **本服务自有** | `since`、`pages`、`page`、`limit` | 我们消费，**不会**发给上游 |
| **原样透传** | `filter_by`、`filter_by_tags`、`sort_by`、`order_by` | 原封不动转发给上游女优页 |

透传的键是本服务**不解释、不改写、不校验**的上游私有契约。
唯一的例外是后三个自有参数被刻意覆盖（见下），还有一处可证明的笔误会被拦下（见 `filter_by`）。

---

## 本服务自有参数

### `since`

只保留发行日期不早于它的作品。

```
?since=2026-01-01
```

- 比较字段：`release_date`（字符串字典序，格式 `YYYY-MM-DD`）
- **解析不了发行日期的作品一律保留** —— 「按错误规则丢弃数据」比「多给几条」危险得多
- 每次启用都会在日志里打一条 WARN，因为**它的语义尚未定稿**（见 ticket 09）
- ⚠️ 一个副作用：`pubDate` 取自磁链的 `created_at`，与 `since` 比较的 `release_date`
  不是同一个日期。因此过滤后仍可能看到 `pubDate` 比 `since` 早的条目
  （合集再版就是这种情况）

### `pages`

翻多少页，默认 **1**，上限 **20**。

```
?pages=3
```

- 默认只取第一页 = 最新的 50 部。对「已有全部旧作、只追新」这个场景**远远够用** ——
  新作品必然在顶部
- 上限 20 是为了防止一个拼错的 URL 把上游拖死

### `page` / `limit`

**本服务覆盖这两个，用户传了不生效。**

- `page` 由 `pages` + 逐页循环控制
- `limit` 固定为 **50**，因为实测这就是服务端上限（传 100/200/500 都只给 50）

之所以要覆盖而不是透传：分页是本服务在管的（要跨页去重、要在空页停止），
让用户同时控制会打架。

## 原样透传的参数

### `filter_by` ⭐ 最重要、也最容易写错

**复合掩码**，不是简单的字母组合：

```
{zone}:{letter}:{id}[:主属性逗号列表::]
```

| 段 | 含义 |
|---|---|
| `zone` | 区域号：`0`=有码 `1`=无码 `2`=欧美 `3`=FC2 |
| `letter` | 实体类型：`a`=女优 `s`=系列 `m`=片商 `d`=导演 `c`=番号 `l`=列表 |
| `id` | 实体 id（女优就是 `/rss/actress/{id}.xml` 里的那个 id） |
| 主属性（可选） | **逗号分隔**的筛选字母 |

主属性字母：

| 字母 | 上游给的名字 | **实际筛的是什么**（2026-10-01 复勘确认） |
|---|---|---|
| `p` | 可播放 | `can_play == true` |
| `m` | 含磁鏈 | `magnets_count > 0` |
| `c` | 含字幕 | `has_cnsub == true` |
| `s` | 單體作品 | 没有对应字段 —— 含义取自上游给的名字 |
| `i` | **上游没给名字** | `has_preview_images == true`（有预览图） |
| `v` | **上游没给名字** | `has_preview_video == true`（有预览视频） |

> 这张表不是猜的，判据是「字母筛出来的集合」与「某个字段把全集分成的两半」
> **逐位重合**。推导方法与证据见下节（以及 `cmd/contractprobe props`）。
> `p`/`m`/`c` 三个字母**同时**符合上游给的名字与实测字段 —— 它们充当了方法的正向对照。

```bash
# ✅ 正确
0:a:EvkJ              该女优全部作品
0:a:EvkJ:c::          只看带中文字幕的
0:a:EvkJ:c,m::        逗号分隔多个      —— 实测生效
0:a:EvkJ:p,m,c,s::    全部四个主属性    —— 实测生效（顺序无关）

# ❌ 错误，且**不会报错**
apmc                  缺实体 id → 静默返回【全站最新作品】
0:a:EvkJ:cm::         主属性拼在一起 → 静默忽略，等于没筛选
0:a:EvkJ:a::          拿实体字母当主属性 → 同上，静默忽略
```

> ⚠️ 主属性合法字母见上面的表：`p` `m` `c` `s` `i` `v` —— **六个都能用**。
> `a` 是**实体类型字母**（actor），不是主属性 —— 把它写在主属性位置
> 会被静默忽略。实测 `0:a:EvkJ:a::` 与 `0:a:EvkJ` 返回**完全相同**。

**两个错误都是静默的**，这是本表最需要记住的一条。因此**推荐留空**
让本服务自动构造 `0:a:<女优 id>`；确实要筛选时才自己写，且务必用逗号。

> 本服务会拦下「主属性拼接」这一种写法并返回 **400**，因为它可证明是笔误
> （单个主属性就是一个字母，多个必须用逗号）—— 不可能误伤合法配置。
> 至于 `apmc` 这种缺实体 id 的写法拦不了：它长得就像一个合法的 zone/letter/id 序列，
> 只有上游知道它其实无效。

### `filter_by_tags` ⚠️ **确认生效**（2026-10-01 更正）

标签 id 的 CSV。标签 id 从 `/api/v1/actors/{id}` 的 `tags[]` 里取。

```bash
?filter_by_tags=10,8
```

**先前这条写的是「当作未验证功能使用」，那是错的。** 逐个试过 EvkJ 的全部 80 个
标签：**每一个都改变了结果集**，而且筛出来的作品确实带那个标签 ——
例如 `filter_by_tags=68`（潮吹）返回的第一条是 `OFJE-665`，
而 `/api/v4/movies/OFJE-665` 的 `tags[]` 里就有 `68`。

当时误判的原因很可能是：只试了少数几个「常见标签」，而它们碰巧在
当页（release 倒序的第一页 50 条）里覆盖面很广 —— 看起来就「与全集相同」。
把 80 个标签全试一遍，`filter_by_tags` 的生效立刻显形。

**一个仍然没有解释的观察**：`tags[]` 里的 `videos_count`（上游声明的「该女优
带这个标签的作品数」）与 `filter_by_tags` 实际筛出的条数**不是一个口径**。
EvkJ 的 80 个标签里有 15 个对不上，而且**两个方向都有**：

```
212(VR)          声明 48、实得 27
48(蕩婦)          声明 26、实得 27
148(主觀視角)      声明 23、实得 24
46(顏射)           声明 20、实得 22
161(16小時以上作品) 声明 11、实得 12
```

「实得更多」这一侧排除了「只是分页截断」这个解释（这 15 个的实得数都小于
当页上限 50，因此没被截断）。具体口径差在哪未查 —— 可能 `videos_count`
只统计某类作品，也可能筛选把共演/合集算进来了。

**实用结论：不要把 `videos_count` 当成「筛选后会有多少条」的预期。**
它不影响「生效」这个结论，但会影响任何想拿它做分页预估的用法。
`contractprobe tags` 会把这类不一致自己点出来。

复跑：`contractprobe tags EvkJ`（逐个标签对照，并落盘每次的 id 清单）。

### `sort_by`

⚠️ 实测**只有一部分值产生不同排序**，其余全部静默回退到 `release`（不报错）。

**实测生效的取值（2026-10-01）—— 这份清单是「下界」，不是白名单：**

| 值 | 结果 |
|---|---|
| `release` | 按发行日期（**这也是服务端默认**） |
| `score` | 按评分 |
| `hit` | 与 release 不同的序（上游无文档，具体含义未查） |
| `update` | 与 release 不同的序 |
| `watched_count` | 与 release 不同的序 |
| `want_watch_count` | 与 release 不同的序 |

这五个都在**完整片单**上验证过：返回的是同一批作品的**重排**
（EvkJ 229 部、83V 173 部，集合完全相同、顺序全不同），因此它们是真的排序键。

> ⚠️ **完整合法取值集从外部不可枚举** —— 这是方法论结论，不是偷懒：
> 黑盒只能**证真**（某个值产生了不同的序 ⇒ 它合法且有意义），
> 无法**证伪**（某个值静默回退到 release，与「合法但恰好同序」在输出上完全一样）。
> **代价**：只能给出「实测生效清单」，不能说「除这些以外都非法」。
> **缓解**：本服务**不校验** `sort_by`（不知道白名单，硬校验会把上游新增的
> 合法值判死），文档只推荐上面这几个值。

**实测没有区分度、因此不应依赖的取值**（与 `release` 逐位同序）：

```
watched  want_watch  number  create_date  created_at  create_at  release_date
updated_at  views  view_count  collect  collect_count  magnets_count  duration
size  random  comments_count  reviews_count  videos_count  views_count
play_count  playback  favorite  favorite_count  likes_count  share_count
download_count  title  id  type  can_play  has_cnsub  new_magnets  play_subtitle
publish_date  made_date  released_at  rank  top  trending  latest
date  hot  new  rating  popularity  view  download  likes  weekly  monthly
```

> 这份「无效清单」**不能当成白名单的补集**用（见上面那条方法论限制）。
> 它的用处是：下次想试某个值时先查这里，省掉一次假设。
> 其中 `watched` / `want_watch` 值得单记一笔：它们是 APK 里 UI 标签
> "Sort by watched count" 的字面词，**但上游不认** —— 认的是 `watched_count`。
> 也就是说「App 的文案」推不出「上游的字段名」，只能实测。

所以**拼错 `sort_by` 不会告诉你**，只会给你发布日期排序。请只用上表里确认过的值。

复跑：`contractprobe sort EvkJ`（两阶段：先全词汇对照第一页，再把生效的值拉全集比对）。

### `order_by`

`desc`（默认）或 `asc`。实测 `asc` 确实生效。
非法值静默回退到 `desc`。

## 服务端默认值（已实测确认）

不传任何参数时，上游的行为是：

| 参数 | 服务端默认 |
|---|---|
| `sort_by` | `release` |
| `order_by` | `desc` |
| `limit` | 20（我们强制为 50） |
| `page` | 1 |
| `filter_by_tags` | 空 |

`sort_by`/`order_by` 的默认值经实测比对确认：不传与显式传

只是让意图明确。

## 女优 id 从哪来

id 就是 JavDB 的短码（如 `EvkJ`），**不是数字**。

两个来源：

1. **`GET /collected`** —— 列出你在 App 里收藏的女优，每条都带现成的 feed 路径
   （需要 token）
2. **App 里女优页的分享链接或 URL**，形如 `https://javdb.com/actors/EvkJ`

## 与先例项目的出入

先例项目 [javdb-cli](https://github.com/FlanChanXwO/javdb-cli) 的实现帮了大忙，
但实测发现三处不能照抄：

1. **主属性必须逗号分隔。** 它的 `BuildEntityFilter` 用
   `strings.Join(main, ",")`，这一点是对的；但它的**测试夹具**里
   `name_zht` 有值，照抄会写错名字读取（见下）。
2. **不要读 `name_zht`。** 实测它在新版服务端上**恒为空**，与 `lang` 无关。
   随 `lang` 变化的是 `name` 本身：

   ```
   accept-language: en     -> name = "Kawakita Saika"
   accept-language: zh-CN  -> name = "河北彩花"
   ```

   因此想要中文名要配 `app_api.lang: zh-CN`，而不是去读 `name_zht`。
3. **它的 `model.MainFlags = {p,m,c,s,i,v}` 没有来源。** 六个字母，零注释。
   其中 `p/m/c/s` 能在上游的 `filter_tags` 里找到对应的中文名，
   `i/v` 找不到 —— 但实测 `i/v` **确实有效**，只是上游不给它们名字。
   教训不是「别信先例」，而是「先例里的常量要按它有没有证据分开对待」：
   本文曾把整个集合当成上游给的事实，还给 `i/v` 编了一个并不存在的出处
   （详见复勘记录第 2 条）。

## 复勘记录（2026-10-01，ticket 03）

本文先前有一个「未验证的部分」小节，列了四条断言。它们现在**全部有结论**，
因此那一节被本节取代 —— 结论留在正文，方法与证据留在这里。

工具：`cmd/contractprobe`（本仓库内，可复跑）。它复用 `internal/appapi`
的传输层与签名，因此它发的请求与服务发的**逐字节同类**；
原始响应落在 `-out` 指定的目录里，作为可引用的证据。

### 1. `i` / `v` 的含义 —— 已确认（`props` 命令）

**结论：`i` = 有预览图，`v` = 有预览视频。**

方法不是猜，是**用字段把全集分成两半**：筛选字母做的就是一次布尔划分，
而列表响应本来就带一批布尔字段。若某个字段的真假划分与某个字母的划分**逐位重合**，
那个字段就是它的含义。这个方法**可以证伪** —— 对不上就老实说「仍未确认」。

```
字母  全集  与它逐位重合的字段
p     83   can_play==true
m    110   magnets_count>0
c     64   has_cnsub==true
s    103   —（没有字段对得上，含义取自上游给的名字）
i    227   has_preview_images==true
v    151   has_preview_video==true
```

（EvkJ，全集 229 部；用 `kzx6`（i=222 / v=166）与 `83V`（i=152 / v=135）复验，
六个字母的对应关系完全一致。）

`p`/`m`/`c` 有上游给的名字，且各自对上了一个字段 —— 这说明方法本身有效。
`s` 没有字段（「作品是不是单体」这个属性不在列表形态里）。

### 2. 关于 `i` / `v` 出处的一处**更正**

本文先前写的是「`i` `v` 含义未确认（来自上游的 `filter_tags`）」。这句话两处都不准确：

- **`i`/`v` 并不出现在 `filter_tags` 里。** 扫过 400 位女优的资料，
  上游给出的 `filter_tags` 词表**只有 `p` `s` `m` `c`** 四个 —— 每个都带中文名：

  | 字母 | 上游给的名字 |
  |---|---|
  | `p` | 可播放 |
  | `s` | 單體作品 |
  | `m` | 含磁鏈 |
  | `c` | 含字幕 |

  （四个 zone 都试过，都是同一份词表；这条端点上的 `filter_by` 不改变结果，
  因此样本是「女优列表 + 排行榜」这一总体，不是按区域采的。）

- **它们的真正出处是先例项目 `javdb-cli`**：`internal/javdb/appapi/model/types.go`
  里的 `MainFlags = {p, m, c, s, i, v}` —— 六个字母，**没有任何注释或来源**。
  本文当时把这个集合当成了上游给的事实，并顺手给它安了一个（并不存在的）
  `filter_tags` 出处。

这条的经验值得留下：**先例项目里的常量，其分量取决于它有没有证据。**
`p/m/c/s` 有上游文案佐证；`i/v` 没有。而事后来看 `i/v` **确实是有效的**
（上游受理，而且筛出的正是有预览图/预览视频的那些）—— 只是上游不在
`filter_tags` 里列它们。也就是说一份没证据的常量既可能是真的也可能是错的，
既不能当事实用，也不能不验证就丢。

### 3. `filter_by_tags` 是否生效 —— 已确认：**生效**

见正文 `filter_by_tags` 一节：EvkJ 的全部 80 个标签逐个对照，
**每一个都改变了结果集**，且抽验返回的作品确实带该标签。
先前记「未确认」是样本太小造成的误判。

### 4. `sort_by` 的完整合法取值集 —— **结论是：不可枚举**

见正文 `sort_by` 一节。已确认生效的五个值：`score` `hit` `update`
`watched_count` `want_watch_count`（另加默认的 `release`）。

完整集合无法从外部确定，原因见正文：黑盒只能**证真**，不能**证伪**。
这不是「还没测」，而是**测不出来** —— 任何「同序」的观察都与
「非法值静默回退到 release」无法区分。

**代价与缓解**：只能给出「实测生效清单」；本服务因此**不校验** `sort_by`
（以免把上游新增的合法值判死），文档只推荐清单里的值。

### 5. 主属性逗号列表的组合语义 —— 已确认：**交集（AND），且顺序无关**

先前只测过「`c`、`c,m`、`m,c`、`p,m,c,s` 生效，顺序无关」，现在把它精确化：

- 六个字母的全集大小：`p` 83 / `m` 110 / `c` 64 / `s` 103 / `i` 227 / `v` 151
  （EvkJ，基线 229）。
- **任意多个字母的逗号列表，结果集恰好等于各单属性结果集的交集，且与交集同序。**
  全部 63 个非空组合逐个验证，无一例外。
- `c,m` 与 `m,c` 逐位同序 —— **顺序无关**。

> 这一条第一版测错了一次，值得记下来：当时只比较 `page=1` 的 50 条，
> 于是「组合 = 交集」这一列几乎全为 false。但那不是上游的问题 ——
> 筛完之后每页的 50 条只是各自集合的一个**前缀**，两个不同筛选条件的前缀
> 本来就不会相等，与语义无关。要谈集合语义就必须把整个片单拉全（229 部 = 5 页）。
> `contractprobe combo` 现在一律拉全集。

### 6. `size` 的单位 —— 已确认：**MiB（2^20 字节）**

判据是拿同一条磁链去 javdb.com 的作品页对照。网页的每个磁链行带
`data-size` 属性，其值与 App API 的 `size` **是同一个整数**，
而网页显示的文字是 `size/1024` 保留两位小数：

| 磁链 | API `size` | 网页 `data-size` | 网页显示 | `size/1024` | `size/1000` |
|---|---|---|---|---|---|
| SONE-360-UC.torrent.无码破解 | 8570 | 8570 | 8.37GB | **8.369** | 8.570 |
| SONE-360-C.torrent | 8050 | 8050 | 7.86GB | **7.861** | 8.050 |
| SONE-360-C.无码破解.torrent | 5530 | 5530 | 5.40GB | **5.400** | 5.530 |
| sone-360.torrent | 8189 | 8189 | 8.00GB | **7.997** | 8.189 |
| SONE-360ch | 6993 | 6993 | 6.83GB | **6.829** | 6.993 |
| SONE-360.mp4 | 8346 | 8346 | 8.15GB | **8.150** | 8.346 |

`size/1024` 六条全部对得上（7.997 显示成 8.00，说明是四舍五入到两位），
`size/1000` 六条全对不上。因此单位是 MiB，网页只是把标签写成了 "GB"。

**对代码的影响**：`catalog.Magnet.SizeMB` 因此改名为 `SizeMiB`
（旧注释写的是「假定为兆字节」）。`internal/feed/rss.go` 里
`enclosure length` 的换算 `* 1024 * 1024` 本来就是对的 —— 只是当时没有依据。
`pin.json` 里旧的 `size_mb` 键会被读入并迁移到 `size_mib`，
否则「读旧文件 → 写回」会**静默把体积清零**（有单测钉住这条迁移）。

### 仍然没有结论的（已登记，不是遗留）

- **`i`/`v` 没有上游文案佐证** —— 含义是从字段反推的。若上游某天让某个字母的
  划分与另一个字段巧合重合，这套方法会认错。缓解：三个女优样本一致。
- **`tags[].videos_count` 与 `filter_by_tags` 实得条数口径不同**（80 个标签里
  15 个对不上，且两个方向都有），原因未查。它不影响「生效」这个结论，
  但意味着 `videos_count` 不能当作筛选结果的预期条数。
- **`size` 单位依赖网页的换算约定** —— 若上游把显示改成十进制，这条判据会失效。
  它只影响 `enclosure length`（qBittorrent 不拿它做判断），因此代价很轻。

### 复跑方式

```bash
go run ./cmd/contractprobe props EvkJ       # 字母含义推导（i/v）
go run ./cmd/contractprobe letters          # 扫 400 位女优的 filter_tags 词表
go run ./cmd/contractprobe tags EvkJ        # filter_by_tags 逐个标签对照
go run ./cmd/contractprobe sort EvkJ        # sort_by 词汇对照 + 全集复核
go run ./cmd/contractprobe combo EvkJ       # 主属性组合语义（交集 / 顺序无关）
go run ./cmd/contractprobe magnets QNN9e4   # size 与网页对照用的磁链转储
```

每个命令都会把原始响应写到 `contractprobe-out/`（`-out` 可改）作为证据。
