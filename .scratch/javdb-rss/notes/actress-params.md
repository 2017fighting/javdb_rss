# 女优订阅的参数表

`GET /rss/actress/{id}.xml?<参数>` 里各参数的权威说明。

**每一条都是 2026-09-30 对着真实上游实测得到的**，不是从文档或先例项目抄的 ——
上游没有公开文档，而先例项目在几处细节上与实测不符（见文末「与先例项目的出入」）。

## 参数分两类

这是最容易搞混的一处，所以先分清：

| 类别 | 参数 | 谁在用 |
|---|---|---|
| **本服务自有** | `since`、`pages`、`page`、`limit` | 我们消费，**不会**发给上游 |
| **原样透传** | `filter_by`、`filter_by_tags`、`sort_by`、`order_by` | 原封不动转发给上游演员页 |

透传的键是本服务**不解释、不改写、不校验**的上游私有契约。
唯一的例外是后三个自有参数被刻意覆盖（见下），还有一处可证明的笔误会被拦下（见 `filter_by`）。

---

## 本服务自有参数

### `since`

只保留发行日期不早于它的作品。

```
?since=2026-01-01
```

- 比较字段：`release_date`（字符串字典序，格式 `YYYY-MM-DD`）
- **解析不了发行日期的作品一律保留** —— 「按错误规则丢弃数据」比「多给几条」危险得多
- 每次启用都会在日志里打一条 WARN，因为**它的语义尚未定稿**（见 ticket 09）
- ⚠️ 一个副作用：`pubDate` 取自磁链的 `created_at`，与 `since` 比较的 `release_date`
  不是同一个日期。因此过滤后仍可能看到 `pubDate` 比 `since` 早的条目
  （合集再版就是这种情况）

### `pages`

翻多少页，默认 **1**，上限 **20**。

```
?pages=3
```

- 默认只取第一页 = 最新的 50 部。对「已有全部旧作、只追新」这个场景**远远够用** ——
  新作品必然在顶部
- 上限 20 是为了防止一个拼错的 URL 把上游拖死

### `page` / `limit`

**本服务覆盖这两个，用户传了不生效。**

- `page` 由 `pages` + 逐页循环控制
- `limit` 固定为 **50**，因为实测这就是服务端上限（传 100/200/500 都只给 50）

之所以要覆盖而不是透传：分页是本服务在管的（要跨页去重、要在空页停止），
让用户同时控制会打架。

## 原样透传的参数

### `filter_by` ⭐ 最重要、也最容易写错

**复合掩码**，不是简单的字母组合：

```
{zone}:{letter}:{id}[:主属性逗号列表::]
```

| 段 | 含义 |
|---|---|
| `zone` | 区域号：`0`=有码 `1`=无码 `2`=欧美 `3`=FC2 |
| `letter` | 实体类型：`a`=女优 `s`=系列 `m`=片商 `d`=导演 `c`=番号 `l`=列表 |
| `id` | 实体 id（女优就是 `/rss/actress/{id}.xml` 里的那个 id） |
| 主属性（可选） | **逗号分隔**的筛选字母 |

主属性字母：

| 字母 | 含义 |
|---|---|
| `p` | Playable（可播放） |
| `m` | Downloadable（可下载） |
| `c` | Subtitles（带字幕） |
| `s` | Individual works（单体作品） |
| `i` `v` | 未确认含义（来自上游的 `filter_tags`） |

```bash
# ✅ 正确
0:a:EvkJ              该女优全部作品
0:a:EvkJ:c::          只看带字幕的
0:a:EvkJ:c,m::        逗号分隔多个      —— 实测生效
0:a:EvkJ:a,p,m,c::    全部四个          —— 实测生效（顺序无关）

# ❌ 错误，且**不会报错**
apmc                  缺实体 id → 静默返回【全站最新作品】
0:a:EvkJ:cm::         主属性拼在一起 → 静默忽略，等于没筛选
```

**两个错误都是静默的**，这是本表最需要记住的一条。因此**推荐留空**
让本服务自动构造 `0:a:<女优 id>`；确实要筛选时才自己写，且务必用逗号。

> 本服务会拦下「主属性拼接」这一种写法并返回 **400**，因为它可证明是笔误
> （单个主属性就是一个字母，多个必须用逗号）—— 不可能误伤合法配置。
> 至于 `apmc` 这种缺实体 id 的写法拦不了：它长得就像一个合法的 zone/letter/id 序列，
> 只有上游知道它其实无效。

### `filter_by_tags`

标签 id 的 CSV。标签 id 从 `/api/v1/actors/{id}` 的 `tags[]` 里取。

```bash
?filter_by_tags=10,8
```

⚠️ 实测未确认它是否真的改变了结果集（用常见标签试时结果与全集相同）。
**当作未验证功能使用。**

### `sort_by`

⚠️ 实测**只有两个值产生不同排序**，其余全部静默回退到 `release`：

| 值 | 结果 |
|---|---|
| `release` | 按发行日期（**这也是服务端默认**） |
| `score` | 按评分 —— 实测确实不同 |
| `rating` `popularity` `want_watch` `hot` `new` `date` `updated` `view` `download` | 与 `release` 相同 |
| 任意拼错的值 | 与 `release` 相同，**不报错** |

所以**拼错 `sort_by` 不会告诉你**，只会给你发布日期排序。本服务不拦这个
（我们不知道上游到底支持哪些值），因此请只用 `release` 或 `score`。

### `order_by`

`desc`（默认）或 `asc`。实测 `asc` 确实生效。
非法值静默回退到 `desc`。

## 服务端默认值（已实测确认）

不传任何参数时，上游的行为是：

| 参数 | 服务端默认 |
|---|---|
| `sort_by` | `release` |
| `order_by` | `desc` |
| `limit` | 20（我们强制为 50） |
| `page` | 1 |
| `filter_by_tags` | 空 |

`sort_by`/`order_by` 的默认值经实测比对确认：不传与显式传
`release`+`desc` 返回**完全相同的顺序**。因此本服务显式写上它们不会改变行为，
只是让意图明确。

## 女优 id 从哪来

id 就是 JavDB 的短码（如 `EvkJ`），**不是数字**。

两个来源：

1. **`GET /collected`** —— 列出你在 App 里收藏的女优，每条都带现成的 feed 路径
   （需要 token）
2. **App 里女优页的分享链接或 URL**，形如 `https://javdb.com/actors/EvkJ`

## 与先例项目的出入

先例项目 [javdb-cli](https://github.com/FlanChanXwO/javdb-cli) 的实现帮了大忙，
但实测发现两处不能照抄：

1. **主属性必须逗号分隔。** 它的 `BuildEntityFilter` 用
   `strings.Join(main, ",")`，这一点是对的；但它的**测试夹具**里
   `name_zht` 有值，照抄会写错名字读取（见下）。
2. **不要读 `name_zht`。** 实测它在新版服务端上**恒为空**，与 `lang` 无关。
   随 `lang` 变化的是 `name` 本身：

   ```
   accept-language: en     -> name = "Kawakita Saika"
   accept-language: zh-CN  -> name = "河北彩花"
   ```

   因此想要中文名要配 `app_api.lang: zh-CN`，而不是去读 `name_zht`。

## 未验证的部分

诚实标注，避免把推测当事实：

- **`filter_by_tags` 是否真的生效** —— 未确认
- **`i` / `v` 两个主属性字母的含义** —— 未确认
- **`sort_by` 的完整合法取值集** —— 只确认了 `release` 与 `score` 有区别，
  无法区分「非法值」与「合法但恰好同序」
- **主属性逗号列表是否支持所有组合** —— 只测了 `c`、`c,m`、`m,c`、`a,p,m,c`
