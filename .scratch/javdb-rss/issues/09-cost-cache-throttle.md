# 请求成本模型：缓存、并发与限流

Type: grilling
Status: resolved
Blocked by: 06

## Question

一个女优 feed 的渲染成本有多大，撑不撑得住 qBittorrent 的轮询频率？

**问题规模**（待 ticket 06 量化）：
- `/api/v1/actors/{id}` 一次返回 N 部作品
- 每部作品要单独拉 `/api/v1/movies/{id}/magnets` 才知道磁链
- → 一个女优 feed = **1 + N 次请求**。N 可能是几十。
- 而 qBittorrent 会**按固定周期**轮询每个 feed，多个 feed 叠加。

要定的：

1. **量级**：一个女优页返回多少部？`/movies/{id}/magnets` 能不能批量？
   一次 qB 轮询最坏会打出多少个请求？—— 这条必须等 ticket 06 的真实响应才能算，
   **算完再来本 ticket 讨论**。
2. **缓存放哪、放多久**：
   - 进程内（map + TTL）：最简单，重启即失效但无害（无状态）
   - 落盘（bbolt / 单文件）：重启不冷启动，仍然可丢弃
   - **只缓存「番号 → 磁链列表」**（贵且变化慢），还是也缓存搜索/演员页？
   目标：把「按请求现算」的 N+1 摊平成「按后台周期算一次，请求读缓存」。
3. **是否有后台刷新**：定时把所有订阅跑一遍，请求只读快照。
   如果有，**刷新周期**取多少、失败怎么退避？
4. **并发与节流**：同时几个 in-flight？每个 host 的 QPS 上限？
   遇到 429 / 5xx 怎么退避？—— 限流参数与「App API 封禁阈值」这条雾一起定。
5. **qBittorrent 轮询下的正确性**：因为无状态，用户把 qB 的刷新间隔设成 5 分钟，
   我们缓存 TTL 设成 30 分钟，feed 内容会抖动吗？同一个 infohash 的 guid 必须**恒定**，
   这条要跟 ticket 08 的 guid 规则对齐。
6. **冷启动**：进程刚起、缓存空、qB 立刻来拉 10 个 feed 会怎样？
   要不要限流排队 / 返回部分结果 / 预热？

## Answer

**已定（2026-09-28 与用户 grill 得出）。结论与我们最初的推荐相反 —— 实测推翻了它。**

### ⭐ 实测推翻了我原来的推荐

我原来说「缓存很可能有必要」，那是基于「上游慢」的假设。**假设是错的。**

响应头揭示的真相：

```
X-Runtime: 0.005328              ← 源站渲染 5ms
Server-Timing: cfOrigin;dur=198  ← 含 Cloudflare 边缘 218ms
```

上游快到几乎不占时间。那 6.1 秒**是我们自己串行发 N+1 请求**造成的。

实测并发效果（一个 50 部女优页）：

| 并发 | 耗时 |
|---|---|
| 1（串行，原状） | 6.75s |
| 4 | 2.22s |
| **8** | **1.30s** |
| 16 | 0.86s |
| 32（34 请求压测） | 1.57s，**零失败、无限流** |

→ **主要收益来自并行化，不是缓存。** 缓存会引入「陈旧数据」这个新概念，
而我们本可以只花并行化这点成本就拿到大部分收益。

### 决定

1. **并行化**：`MagnetConcurrency` 默认 **8**（可配）。选 8 是因为它已过收益最陡的一段
   （16 只再快 0.44s），而我们是第三方上游的客人，不该为那点时间施加双倍并发。
2. **singleflight**：合并并发的相同请求。**它不是缓存** —— 不存任何东西，
   只在「此刻飞行中」合并，因此不返回陈旧数据、不占内存、重启无影响。
3. **不做 TTL 缓存**。用户的轮询间隔是 qB 默认 **15 分钟**，远大于任何合理 TTL，
   缓存基本不会命中 —— 加了只是引入复杂度。
4. **不做后台刷新**。它会要求「已知订阅清单」，与已定的「URL 即订阅 + 无状态」直接冲突。

### 翻页

用户选「默认第一页 + 可选 `?pages=N`」。

- 默认只取第一页（最新 50 部）—— 用户的需求是「已有全部旧作、只追新」，
  新作品必然在顶部，第一页远远够用
- `?pages=N` 供「从零建库」这类场景，**上限 20 页**（防一个 URL 拖死上游）
- 每页仍按 50 条（实测服务端上限）
- 页内磁链并行；跨页**不**并行，保持上游压力可预测

### 实测结果

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 女优 feed（50 部） | 6.1s | **1.8s** |
| 番号 feed | 1.2s | **0.95s** |

### 交付

- `internal/singleflight/`：自己实现（同 x/sync/singleflight 语义），零新依赖。
  含 panic 保护 —— 否则一个编程错误会让所有等待者永久挂在 `wg.Wait()` 上。
- `internal/dedupe/`：`catalog.Source` 装饰器。**这是「Source 是唯一外部边界」
  设计的第一个实际收益** —— 加这一层没有改动 httpapi / feed / appapi 任何一行。
- `internal/appapi/source.go` 的 `hydrate` 改为并行，结果**严格按输入顺序**返回
  （并发不得打乱 feed 顺序）；任一磁链请求失败即整次失败（静默漏片比报错更危险）。
- `app_api.magnet_concurrency` 配置项，默认 8。

### 测试

- singleflight：9 条（含「不缓存」「panic 不挂死」「同 key 合并」「异 key 不合并」）
- dedupe：8 条，**含安全性关键项**：参数不同的请求绝不能被合并
  （合并错 = 用户拿到别人的订阅内容），以及参数书写顺序不影响 key
- 全部离线；`go test -race ./...` 干净
